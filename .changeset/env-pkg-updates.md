环境自检里 dsh 那一行也有「更新」入口了，而且和 pnpm 一样**带版本比对**。

起因是"我希望能在 dsh console 的环境自检页进行手动升级"：原来只有 pnpm 有行内更新入口，dsh 只能靠
外部的 `npm i -g @deepseek-ai/dsh`。现在两行都在行上写出「当前 → 目标」（`更新 dsh → 0.2.0-rc.2`）。

**按钮只在真有新版本时出现**（用户裁定）：还没拿到读数（初始状态）、已经是最新、这一轮没查到，都
不给按钮 —— 已是最新时按钮位上只留一句读数（无按钮）。唯一的例外是本机那一份 dsh **实测跑不动**
时给「重装 dsh」：那不是更新，是修（pnpm 不需要这条例外，它跑不动时那一项本身就是"不可用"，
走既有的「一键安装 pnpm」）。

几处值得知道的取舍：

- **不新增动作**：两个入口都复用既有的 `install-pnpm` / `install-dsh`（命令一字不改），确认区也是同一份
  —— 界面上看到的命令原文与目标目录仍然只来自主进程现算的计划。
- **目标版本必须等于那条命令真的会装到的版本**。不带版本的 spec 取 registry 的 `latest` 标签，**不能**
  取"列表里最新的"：`@deepseek-ai/dsh` 一个稳定版都没有（`latest` = 0.2.0-rc.2，而最新的发布是
  0.2.1-alpha.1），取"最新"会出现"提示有新版本、点了装不到"并且**永远不收敛**；`pnpm` 的 `latest`
  （12.8.1）同样落后于已发布版本（12.9.0）——这个坑是真机数据查出来的，不是推论。
- 缺 VC++ 运行库时 pnpm 走纯 JS 那条线（`pnpm@10`），目标按**主版本区间里最高的已发布版本**取：range
  解析看版本序、不看标签，这样才和命令一致。
- 版本比较是完整 semver（含预发布段），所以 `0.1.5-rc.1` 会正确地看到 `0.2.0-rc.2` 是一次升级；**没有**
  复用 Console 自己更新那个 `compareVersions`（那个故意把预发布当同版本）。
- 查询是**只读**的：一次 `GET`，用设置里的「插件安装源」（留空走官方源），不改用户的 `.npmrc`；失败
  （超时 / 断网 / 非 2xx）一律当作"这一轮查不到"，那时**不给按钮也不编结论**（见上一条的显示条件）。
- 它**不进 `EnvDoctorReport`**：那条路首启门禁也在读，塞网络请求会把门禁变成"断网就进不去"。所以是
  一条按需的只读通道 + 5 分钟缓存，只在详情层打开 / 重新检测 / 修复完成之后拉一次。
- **升级 dsh 之前不停 dsh**（npm 换的是磁盘上的文件，跑着的进程已经加载完了），与"更新 Node"相反；
  收口是更新完成后提示「重新启动 dsh 之后新版本才生效」并给一键重启。

真机验证时又抓出一个 bug，这一版一并修掉：**点「更新 dsh → 0.2.0-rc.2」装完重启不生效**。

- 症结是"更新 dsh"用的 npm 与**被升级的那份 dsh** 不是同一棵树：console 用的是 nvm 里 v24.14.1 那份
  dsh，而 npm 是从 PATH 上找到的（这台机器上是 vite-plus 的 `vp` 转发器）→ 升级装进了 v22.17.1。
  结果那份 dsh 一个字没变、行上却仍写着有新版本 → **不收敛**。
- 现在的规则（`src/main/dsh-npm.ts`）：**dsh 由「`<node>` + `dsh/lib/bin.js`」起来时，npm 必须是与那个
  node 同目录的那一份**；还没装 / 只能靠 `npx` 起来时保持原样用系统 npm（新装一份）。
- 认不出"它属于哪个 Node"（shim / 自定义命令），或那份 npm 不存在/不可执行时**不给更新入口**，
  改为在 dsh 那一行写一条诚实边界（说不准该装进哪个 Node 的全局目录 + 一条可自己执行的命令 + 重新检测）。
- **解析收口成一份**并按进程缓存，报告侧与执行侧读同一个值 —— "显示的命令 == 执行的命令"不再靠运气；
  「会装进 …」也改成按**计划里那一条 npm** 分别问（install-dsh 与 install-pnpm 可能不是同一个 npm）。
- `install-pnpm` 的 npm 解析一个字没动；`findNpm()` 把转发器当成 npm 那个假阳性按方案 A 暂不修，
  已在 `docs/env-doctor.md` 记为已知问题。

方案 A 只是**绑对了用哪一份 npm**，根因还在：**装到哪棵树不由那份 npm 决定**。

- 症结：起修复子进程时用的是 `{ ...envWithKnownBins(process.env) }`，而它只改 PATH —— 父进程里那整套
  `npm_config_*` 被**原样传给了 npm**。npm 的优先级是"环境变量 > 由自身位置推出的默认值"，于是
  `i -g` 的全局目录由继承来的键决定。真机实测（拿 v24.14.1 那份 npm 跑 `prefix -g`）：

  | 试验                                                  | 结果                                    |
  | ----------------------------------------------------- | --------------------------------------- |
  | 现状（继承的 env）                                    | `…/nvm/versions/node/`**`v22.17.1`** ❌ |
  | 只清 `npm_config_global_prefix` + `npm_config_prefix` | 仍是 v22.17.1 ❌（清这两个**不够**）    |
  | `env -i`（只给 PATH / HOME）                          | `…/nvm/versions/node/`**`v24.14.1`** ✅ |
  | `env -i` + 只放回 `npm_config_prefix=…v22.17.1`       | v22.17.1（**单这一个键就能翻转**）      |

- 修法：新增纯函数 `cleanNpmEnv(base)`（`src/main/process-path-env.ts`，与 `envWithKnownBins` 同一个家）
  —— **丢掉所有 `npm_config_*` / `NPM_CONFIG_*`（大小写不敏感、按前缀匹配）**，其余原样保留
  （PATH / HOME / 代理 / locale 一个不动）。判据是**前缀**而不是固定清单：npm 的配置键是开放的，
  列清单必然漏，而"只清两个键"就是漏的那种。
- 调用点的顺序有意义：**先清、再注入**（`cleanNpmEnv(envWithKnownBins(process.env))` 在前，
  `pluginRegistryEnv(...)` 在后），否则设置里填的安装源会被一起清掉。用户写在 `~/.npmrc` 里的
  registry 不受影响 —— npm 仍会读 userconfig。
- **插件装 / 卸 / 升级那条 pnpm 链吃同一套继承变量，本轮没动**（已记进文档的已知问题）。
