### 0.2 t29 追加裁定：VM-14 / VM-15（归属 → 方法、档位 → 目标档）

**背景（真机实测）**：用户在一台 **Node 由 nvm 管**的机器上（`…\Author Software\nvm\installs\v26.9.0\node.exe`）点「更新 Node.js」，
拿到的计划却是 `msiexec /i node-v24.21.0-x64.msi` → `C:\Program Files\nodejs`（**VM-14**：方法被写死成直装，
照它执行这台机器上会有两份 Node）；而门禁里的档位默认是 `'lts'`、切换入口只是确认区里一行小字，
用户没意识到自己选了「当前版」，于是"更新"的目标（`lts` = v24.21.0）比已经装的那个（`current` = v26.9.0）**更小**
（**VM-15**："更新"看起来像降级，界面没说这是换档）。

## 2. 冻结：「环境 OK」的判定与门禁放行（纯函数边界）

### 2.1 输入与输出

```ts
/** 唯一的门禁判定（与 judgeEnvironment 并列、同处 src/main/env-doctor.ts） */
export function judgeWizard(report: EnvDoctorReport, skips: EnvWizardStepId[]): EnvWizardState;
```

- **输入**：`report`（阶段一判定的产物，形状见契约 `EnvDoctorReport`）+ `skips`（来自设置 `envSkips`）。
- **输出**：`EnvWizardState`（契约 §3.1）。
- **纯函数约束**（与 `judgeEnvironment` 同款，要写成断言）：不碰磁盘、不起子进程、不读 `process.env` / `process.platform` / `process.versions`、不看时钟（`report.checkedAt` 由采集侧给）。**任何输入都不抛**。

### 2.2 判据表（逐条实现）

**第一步：每个步骤的状态**

| 步骤   | `checkIds`                      | 判据满足（`done`）的条件                                         |
| ------ | ------------------------------- | ---------------------------------------------------------------- |
| `node` | `node` / `node-version` / `npm` | `node.status !== 'missing'`                                      |
| `pnpm` | `pnpm`                          | `pnpm.status !== 'missing'`                                      |
| `dsh`  | `dsh` / `dsh-run`               | `dsh.status !== 'missing'` **且** `dsh-run.status !== 'missing'` |

判据**不**满足时按下面三条决定状态，顺序即优先级：

1. 该步骤在 `skips` 里 **且** 它 `skippable` → `skipped`；
2. 该步骤的 `checkIds` 里**至少有一项是 `missing`** → `todo`（明确缺东西）；
3. 否则（一项 `missing` 都没有，只有 `warn`）→ `unknown`（这一轮测不出来）。

`report.error !== null` 时：**只把"没有 `missing` 证据"的步骤记为 `unknown`**；有 `missing` 证据的步骤仍是 `todo`（有证据就挡）。

**第二步：门禁状态**

| 门禁      | 条件                              |
| --------- | --------------------------------- |
| `blocked` | 至少一个步骤 `todo`               |
| `unknown` | 没有 `todo`，但至少一个 `unknown` |
| `open`    | 其余（全是 `done` 或 `skipped`）  |

**第三步：当前步骤（R-05 的结论）**

```
currentStepId = 第一个 todo 的 id
                否则 第一个 unknown 的 id
                否则 null
```

推论（要写成断言）：**`gate === 'blocked'` 时，`currentStepId` 一定是 `todo`**；因此"当前步骤卡"永远有可做的动作（装 / 开始 / 换路），不存在"只有一句结论的卡"。

**不可跳过的步骤**：`node` 与 `dsh` 的 `skippable === false`。写进 `skips` 的 id **被忽略**（不是报错、也不是生效），未知 id 同样忽略。

**逃生口与这个判定无关**：逃生是渲染层的相位（`escaped`），判定函数对它一无所知；逃生**不写盘、不改变 `report`、不改变 `skips`、不改变任何判定结果**。`gateVisible`（渲染层）见 R-08 的三条 disjunct（不是简单的"相位 ∈ {checking, blocked}"）。

### 2.3 快速探测（启动瞬间，R-14）

```ts
/** 只读文件系统：node / npm / pnpm 三个路径 + 本地 Shell；不起任何子进程 */
export function collectBootProbe(settings: SettingsValues, runtime: EnvRuntime): EnvProbeRaw;
```

- 它填 `EnvProbeRaw` 时，**需要子进程才能知道的项**（`node` 的版本、`npm` / `pnpm` 的输出、`dsh` 的实测）把 `skipped` 标成 `true`；`node` / `npm` / `pnpm` 的**路径**照实填（找不到就是 `null`，那是真实证据）。
- `judgeEnvironment` 的新规则：**`skipped === true` 的项一律判 `warn`**，`detail` 写「这一轮没测」（**不是 `missing`**）。这条要覆盖 `node-version` / `npm` / `pnpm` / `dsh` / `dsh-run` 五项。
- 主进程的启动决策（R-14）：`judgeWizard(judgeEnvironment(collectBootProbe(...)), skips).gate === 'blocked'` → **不自动拉起 dsh**；否则照阶段一立即启动。1.5 秒后的完整探测照旧跑。
- 快速探测**不许**起子进程、**不许**重复实现 PATH 查找（R-19）。

**四条约定**（要写成断言，见 `docs/env-wizard.md` §12 第 29–35 条；**t7 对 ② 与 ④ 各加了一条标注，原文保留**）：
① `needChoice !== null` ⟹ `usable === false`；② `direction === 'older'` ⟹ `switchesChannel === true`（"更新"永不降级）；
③ 报告里的 `nodeOwner` 与计划里的 `owner` 出自**同一个纯函数**（同一个导出；全仓库没有第二处路径判断）；
④ 自检页的更新入口（`renderer/panes/EnvPane.vue`）**不许**给 `envNodePlan` / `envNodeInstall` 传 `channel`。

> **⚠️ t7 标注 A（② 的成立方式：按构造，不是"现实中不会发生"）**：`switchesChannel` 的实现在 `decideNodePlan()` 里是
> `direction === 'older' || (currentChannel !== null && channel !== currentChannel)` —— 即「**档位变了 或 目标更低**」这个**超集**语义，
> 所以 ② 在**所有**分支上无条件成立（含 `install` 的设计默认正好跨档那条可达路径：已装当前版的机器上点「安装」→ 目标是稳定版 → 跨档 + 更低）。
> **⚠️ 同一处要记住的坑**：`src/shared/ipc.ts` 里 `switchesChannel` 那句注释只写了**充分条件**（"目标档位与当前档位不同 = 这是换档"），
> **照注释把它改回"只比档位"，`older` 就会重新变成一次没有解释的静默降级**（t9 的变异实验正是这么把它还原红的）——
> **以代码里按构造的那一句为准，别照注释改**；这条纪律写进了 `AGENTS.md` 7.21。
> **⚠️ t7 标注 B（④ 改判成行为式）**：这条原来写成"那个文件里不出现 `channel:`"，与需求 §8.5 第 3 条

> 船长裁定：**以后两者为准** —— **默认不传档位**（`update` 省略 = 跟随当前档、`install` 省略 = 设计默认），
> **只有用户显式选档才传** `channel`。理由：④ 的本意是**防"默认硬编码档位"**（VM-15 的成因），不是禁止显式换档；
> 落地的静态断言盯的是**不许写死默认**（`method: 'direct'` 与 `channel: 'lts' | 'current'` 的字面量都不许出现）。

> **⚠️ t7 标注 C（「原样一句」管的是哪一句）**：需求 §7.9 第 4 条那句"原样一句"（`这样这台电脑上会有两份 Node…`）的适用范围是

> **⚠️ t29 标注（VM-14）：这条路的"前半段"要按机器上有没有版本管理器分岔。** 上面写的流程是
> 「先下载并安装版本管理器的安装包 → 再用它装 Node」——那是**机器上还没有版本管理器**时的路。
> **机器上已经有一个可辨认的版本管理器时（`nvm.exe` 在位 / 模型推得出根），不许再装一遍它**：
> 这次**没有任何东西要下载**（`EnvNodePlan.installsManager === false`，`url` 只指向发布页当出路），
> 流程就是「`nvm install <目标版本>` → `nvm list` 核对 → `nvm use <目标版本>` → 实测复检」。
> 理由：用户点的是"更新 Node"，不是"重装版本管理器" —— 那会多几十 MB 下载、重写它自己的偏好与 PATH 条目，
> 确认区还会说一句与用户意图无关的话。**归属 → 方法**的完整表在 `docs/env-wizard.md` §7.8。> 模型与证据优先级见 [`docs/env-wizard.md`](env-wizard.md) §7.6。

**提权那一次（F-02 / F-03）**：`runElevated` 是**异步**的（`spawn` + `waitForClose(..., 'stop-waiting')`），
并且**先 `publish` 状态再起进程** —— UAC 对话框出现之前，界面已经拿到
「正在请求一次管理员权限、请在弹出的窗口里选择。」。四种结果各自的去路：`ok` 继续；
`declined` / `failed` → `elevationFailure()`；**`timeout` → 先按"未确定"发布，再事实复检**
（重读 PATH + 跑 `<NVM_SYMLINK>\node.exe --version`）：链接已建好就改口说"已经落地"、
提权进程还在跑就保持未确定、进程结束且链接没建才报 `elevation-timeout`（**不是** `symlink`）。

**发布 API 的地址（R-27）**：用 `https://api.github.com/repos/nvm-windows/nvm/releases`；旧的 `coreybutler/nvm-windows` 路径会 **301** 到同一个仓库（id 24268127），**跟随重定向是被允许的、不是错误**，但代码与文档都以新路径为准（同时不要让 301 变成"取不到发布信息"的失败分支）。

**两条"为什么不复用既有实现"的说明**（评审会问）：

- `compareNodeVersions` **不复用** `src/main/updater.ts` 的 `compareVersions`：那个比的是应用版本号、且 `updater.ts` 顶层 `import electron`；安装引擎要保持可离线测（自检与反例脚本要直接 import 它）。两者都短，各管一个域。
- `isElevatedProbeOutput` 只做**判定**（喂输出与退出码），真正起那次只读探测的子进程在 `plan()` 里；这样判定可以在任何平台上用夹具测。

export class NodeInstaller {
  constructor(settings: Settings, hooks: NodeInstallHooks);

  /**
   * 计划（确认区用）。**失败分两种，别混**（R-25 / R-27 落地后按 t5 的实现定稿，逐条对应
   * `src/main/node-installer.ts` 的 `buildPlan` / `buildDirectPlan` / `buildNvmPlan`）：
   *
   * **`null` —— "连版本清单都算不出来"（只有这四类；界面给"拿不到版本清单" + 换源 / 官方下载页 / 重新检测）**：
   * 1. 平台不是 win32（R-20：自动安装只在这一个平台提供）；
   * 2. `index.json` **取不到**（网络类）；
   * 3. `index.json` 解析不出来，或该档（稳定版 / 当前版）**挑不出条目**；
   * 4. 兜底：算计划的过程本身抛了异常（`plan()` 捕获后也返回 `null`，**不抛**）。
   *
   * **`usable: false` + `refuseReason` —— "目标版本定了，但这条路径现在不能走"**（界面照常显示版本与来源，
   * 只是**不给「开始」**；`note` = 原因 + 出路，给人看）：
   * - 官方直装（`method: 'direct'`）：
   *   a. 认不出这台电脑的架构 / 版本号（连地址都拼不出来）→ 不支持类：「这个版本没有适合这台电脑的安装包。」；
   *   b. **校验清单取不到**（连不上 / 超时）→ **网络类**：「没能取到官方的校验清单（连不上或超时），
   *      所以这一次没法确认安装包是哪一个。」—— **不许降级成"这台机器不支持"**；
   *   c. 校验清单里**没有** `node-v<版本>-<arch>.msi`（= 这个档确实没给这台机器出包）→ 不支持类：
   *      「这个版本没有适合这台电脑的安装包。」。
   * - 版本管理器（`method: 'nvm'`）：
   *   d. **提权态**（当前进程是管理员）→ R-23 的原话（「请不要用管理员身份运行 DSH Console 来安装
   *      版本管理器…」）；`isElevated()` 为真时**先于**任何网络请求判断；
   *   e. **发布信息取不到** → **网络类**：「没能取到版本管理器的发布信息（可能连不上，也可能这一会儿
   *      访问太频繁）。」—— **匿名限流也归这一类**（与"取不到校验清单"同一形状，不写 `null`）；
   *   f. 发布里**没有适合这台电脑的架构**的安装包（跳过预发布 / 草稿 / `*-sync.exe` 之后仍挑不到）→

   * 两种结果都不抛。

    method: EnvNodeMethod;
    mode: EnvNodeMode;
    channel?: EnvNodeChannel;

    method: EnvNodeMethod;
    mode: EnvNodeMode;
    channel?: EnvNodeChannel;
  }): Promise<EnvInstallState>;

  state(): EnvInstallState;

  /** 自己有没有在跑（编排用它合成全局忙位） */
  busy(): boolean;

  /** 应用退出时调用：下载 / 校验 → 取消 + 删临时文件；安装 / 等待 → 放弃引用、不杀、不等 */
  detachOnQuit(): void;

  /** 当前 Node 是哪条路管的（界面决定「更新」走哪条；也是 R-09 「换一个 Node」的判据） */
  currentNodeOwner(): 'nvm' | 'system' | 'unknown';
}

**`run()` 的解析时机（必须冻结，否则渲染层的 `await` 会挂住）**：`envNodeInstall` 的 Promise 在这些相位解析 —— `done` / `cancelled` / `error` / （`waiting` 且 `detached === true`）。此后状态继续由 `onEnvInstallState` 推（安装器可能仍在后台跑）。

**若干实现约束（review 项）**：

- 安装器用完整路径 `<SystemRoot>\System32\msiexec.exe`（**不经 PATH 查找**），仍经 `launchSpec()`（PE 直连）；
- 子进程环境 = `envWithKnownBins(process.env)` + 安装源注入（照既有一键修复的做法：只注入这一次进程，不写用户配置文件），`cwd` 固定、`stdio: ['ignore','pipe','pipe']`、**不拼 shell**；
- 新 PATH 生效：从系统里**重读**（用户级 + 机器级），`mergePathFromRegistry` 合成后**并进我们给子进程用的那份环境**；**不写系统 PATH**；
- 下载走 Electron 的网络栈（遵循系统代理）；下载到用户数据目录下的临时目录，取消 / 失败 / 退出时删掉；
- **计划阶段**（`plan()`）：官方直装的存在性与哈希都来自 `SHASUMS256.txt`（R-25），`releaseSigning` 恒为 `'unknown'`；nvm 那条路按发布元数据算 `releaseSigning`（R-27），拿不到发布信息就 `'unknown'`。**计划阶段不读任何文件的签名**，`signer` 恒为 `null`；
- **下载后**（`run()`）：哈希与清单/摘要不一致 → **不安装**（硬性）；没有哈希可比 → 官方直装不给「开始」（计划阶段就拦下）、nvm 旧线按 `sha256: null` 走"这次没能校验安装包的完整性"确认；再读安装包的 Authenticode 签名 —— 有效 → 记录签名者；**明确未签名 / 无效** → `releaseSigning === 'unsigned'` 就继续、否则**不安装**；读不到 / 不明确 → 继续并如实写「这次没能读到安装包签名」；
- 任何时刻只有一次动作（`busy()` + 编排的忙位，§4.4）。

## 6. 实现顺序与交接

**顺序是硬要求**（契约不落地，另外两个模块没有可编译的类型面）：

1. **契约与编排**：先落 §3 的契约（`ipc.ts` + `DEFAULTS` + preload 7 个成员）+ `EnvProbeRaw.skipped` 与 `judgeWizard` / `collectBootProbe` 的骨架（可以先返回最小实现），让另外两个模块能编译；
2. **安装引擎**：纯函数（可离线测）→ 有状态部分（下载 / 校验 / 安装 / 复检 / 停与不杀）→ `detachOnQuit()`；
3. **渲染层**：门禁层（三种屏 + 左轨 + 底条）→ 三步卡与确认区 → 进度与结果 → 自检页增量 → 单独接线与样式；
4. 每个模块**独立验证**（实现者自证 + 独立验证者）→ **集成收口**（changeset + §5.4 的文档同步 + 四道门禁复核）。

**交接物（每个模块都要给）**：① 改了哪些文件（对照 §5.1）；② §3.8 里属于它的断言清单（判据 + 期望）；③ §7 里属于它的人工验证项与证据；④ 它依赖的假设（例如"编排会先落契约"）。

**并行边界**：安装引擎与渲染层可以同时开工（引擎对外只有类 + 纯函数，渲染层对外只有组件 + `lib/**` 的 ref）；两边都**不许**顺手改 `ipc.ts`。

## 9. 冻结之后的改动规则

1. 这份文档是**研发的动工依据**：实现与它冲突 → 先改这里（走一次 product / interaction / visual 三方确认），再动代码。
2. **契约成员不许"顺手加"**：新增 / 改名 / 删字段都要同步 §3 + `preload` + §3.8 的断言；`ipc.ts` 零 `import` 是硬约束。
   **t29 补充**：§3 的逐字块与 `src/shared/ipc.ts` 是被自检 `契约（F-03）` **逐字比对**的 ——
   §3.2.1（t29 增量）落地时，**`ipc.ts`、§3.2 / §3.3 的逐字块、§3.8 的断言必须同一次改完**，
   否则 F-03 先红；加字段时按 §3.2.1 的字段名与注释逐字照抄（含 §3.2.1 里那四条"要写成断言"的约定）。
3. 三份上游规格继续存在，但**只当理由与背景**：任何细节以本文为准（§1.3 已经列出被作废的表述）。
4. 本文**不写会随实现漂移的数字**（自检项数、断言条数、行数）：脚本自己会报（`node scripts/selftest-sandbox.mjs` 与它自动收录的 `scripts/*-cases.mjs`）。
5. 两处**留待工程决定**（只有这两处，其余全部已裁定）：
   - **渲染层**决定内部组件怎么拆分（`shell/EnvGate.vue` 里是否再拆子组件、拆几个）—— 只要不越出 §5.1 的文件清单；
   - **安装引擎**决定下载器与 Windows 提权探测的**具体实现手段**（Electron `net` / `session` / 哪一条命令），只要满足 §4.2 的约束与 §7 第 5 条的证据要求。
6. **同步阻塞的边界（F-03 的裁定，t24 落定）**：安装引擎里**会长时间等用户**或**会被用户操作路径触发**的两处探测必须是异步的 ——
   - `runElevated`（UAC 最长等 5 分钟）：异步 `spawn` + `waitForClose(..., 'stop-waiting')`，**先 `publish` 状态再起进程**；
   - `isElevated()`（`whoami /groups`，15 秒上限）：异步 `runProbeAsync`，因为它会被 `plan()`（用户在确认区切选项）调用。
     **理由**：同步阻塞会把主进程的事件循环停住，先发的状态根本渲染不出来 —— 用户看到的是"应用卡死"，连"要不要点这个 UAC"都不知道；这是可用性故障，不是风格问题。
     **例外（保持同步，明确记为可接受）**：毫秒级、且处在一次性准备阶段的小探测继续用同步 `runProbe`（`reg query` 读两段 PATH / 开发者模式、`Get-AuthenticodeSignature`、`<node> --version` 这类）——
     它们的期望耗时是几十毫秒，15 秒上限只在机器已经不正常时才会碰到；把它们全改成异步会让"校验顺序"这条链多出一串 await 点，收益不抵复杂度。**这条边界是裁定，不是实现细节**：以后要新增"等用户"的探测，按第 6 条办。

## 10. 残留风险与明确不做的事

**残留风险**（实现时要知道，评审时要问）：

1. **真实安装无法在本仓库的沙箱里验证**：所有下载 / 安装 / UAC 路径只能静态检查 + 人工验证（§7）。因此"安装器用了哪些静默参数""装完之后注册表里长什么样"这类细节**必须在真机上确认一次**。
2. **GitHub 发布 API 的匿名限流**：版本管理器那条路要读发布资产（拿 sha256 与下载地址）。匿名请求有频次上限，失败时**不缓存、不重试静默换源**，直接给"打开官方发布页"+「重新检测」这条出路。
3. **版本管理器从 v1 到 v2 的资产命名变过**（`nvm-setup.exe` → `nvm-<版本>-<amd64\|arm64>-setup.exe`，且**它叫 `amd64` 而我们这边叫 `x64`**）：引擎必须**按模式在发布资产里挑**（跳过预发布、跳过 `*-sync.exe`、按架构匹配并做 `x64` → `amd64` 映射），**不许写死文件名**（R-27）。
   **仓库改址**：`coreybutler/nvm-windows` 的 API **301** 到 `nvm-windows/nvm`（同一仓库 id）—— 走 HTTP 客户端时要跟随重定向，并把"301"与"取不到发布信息"分开处理（R-27）。
4. **默认选出来的那一版就是未签名构建**：最新非预发布稳定版 `v2.0.0` 标的是 `Unsigned`（`v2.0.1-hotfix.2` 标 `signed` 但它是 prerelease）。所以"未签名要额外确认"**不是边缘分支**，评审与文案都不许按边缘情况对待（R-27）。
5. **`/qb` 这类安装器参数的可视性**未在真机验证：要求是"安装过程对用户可见 + 我们拿得到退出码"，具体参数由安装引擎决定（§9 第 5 条），但要在 §7 第 3 条里留证据。
6. **nvm v2 的 shim 模式在真机上的 PATH 行为**：我们靠"重读系统环境"来接它（§4.2）；如果真机上它写在别处，`detectNodeOwner` 与 `windowsBinCandidates` 的既有候选都可能认不出来 —— 这是 §7 第 2 条必须留证据的原因。
7. **签名读取本身可能"读不出来"**：Authenticode 的读取在我们这条链路上是"能读到就说、读不到就照实说"，因此**不能**把"读不到"当成"未签名"（那是 R-26 修掉的那个 bug）—— 评审时要专门问这一条有没有分支写反。

**明确不做**（与需求 §14 一致，实现时不许"顺手做"）：

- 不做便携 ZIP 的 Node 安装（会造出第二个事实来源）；
- 不做"跳过门禁"的设置（逃生口已经覆盖真实需求）；
- **不主动提权**（提权只由安装器自己触发；版本管理器那条路遇到提权直接拦下，R-23）；
- 不改系统 PATH、不写用户的 `.npmrc` / nvm 配置文件（只重读、只注入这一次进程）；
- 不做静默安装（任何改动前都有确认区）；
- 不做自动回滚 / 自动卸载；
- 不做任意版本选择器（只有稳定版 / 当前版两档）；
- 不做 macOS / Linux 的自动安装（门禁与 Node 安装只在 Windows 生效，R-20）；
- 不把"正在跑的 dsh"之外的进程停下来；
- 不在诊断与文案里输出任何凭据或环境变量的值（路径可以打，值不行）。
