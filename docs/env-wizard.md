这份文档是**阶段二的唯一需求来源**。交互规格、视觉规格、三个研发模块（安装引擎 / 契约与编排 / 渲染层）与验证都从它出发；与它冲突的表述以它为准，改动它要走一次「冻结 → 改需求 → 再冻结」。

一句话概括要做的东西：

```
一台什么都没有的 Windows 11 上第一次打开 DSH Console
  └─ 先只读地看一眼这台机器（复用阶段一的探测，不重复实现）
       ├─ 环境够用 → 照旧：自动拉起 dsh → 进主界面
       ├─ 明确缺东西（有证据）→ 硬门禁：向导层盖住主界面，逐步引导
       │    ├─ 第一步 Node：两条路可选 —— 直接装官方稳定版 / 通过 nvm 装
       │    ├─ 第二步 pnpm：一键装（可选跳过）
       │    └─ 第三步 dsh：一键装（不可跳过）
       │         └─ 每一步都：确认区 → 跑（可中断）→ 自动复检 → 下一步
       │              └─ 环境 OK → 「进入 DSH Console」按钮（不自动跳走）
       └─ 测不出来（我们的探测失灵）→ 不挡，进主界面 + 常驻黄条 + 向导入口
  └─ 逃生口全程可达：任何时刻都能「先进入界面」，之后再从界面回来
进主界面之后
  └─ 环境自检页（阶段一那一页）多两个按钮：更新 Node.js / 更新 pnpm
```

## 0. 这份文档回答的四个问题

用户的原话拆开是四件事，本文按这四件事组织（第 4~8 节），另外补上权限与网络（第 9 节）、纯净机器的完整走查（第 10 节）、契约增量（第 11 节）、验证映射（第 12 节）：

1. **一个纯净的电脑也能方便地用 dsh**：打开时先检查环境；
2. **没有 Node 就给一个按钮**，点一下自行安装最新稳定版，**并且能在「直接安装」与「通过 nvm 安装」之间选**；
3. **然后逐步引导装 pnpm 等其他环境，直到环境 OK 才可进入我们的页面**（硬门禁 + 逃生口）；
4. **进页面后，环境自检那里支持更新 Node 和 pnpm 的版本**。

## 1. 要解决的问题

阶段一让「为什么起不来」变得可解释，但它**只解释、不解决装 Node 这件事**：机器上连 Node 都没有时，用户看到的是一行红灯加一句「去 nodejs.org 下载」。对开发者这是常识，对一个「拿到安装包、双击、想直接用」的用户这就是死路：

| 现象                                                  | 真实原因                                                                    | 阶段一给的东西               |
| ----------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------- |
| 装完 DSH Console，点开始，界面上就是「已停止」        | 机器上没有 Node，或者 dsh 没装（也没有 npx，因为 npx 自己也要 Node）        | 红灯 + 「去官方页面下载」    |
| 用户不知道装 Node 该选哪个安装包、要不要管理员权限    | 官方下载页有 msi / zip / 7z、x64 / arm64、LTS / Current，全是给开发者看的   | 一个外链                     |
| 装完 Node 之后还是显示「找不到」                      | Windows 上 GUI 应用拿到的是**启动那一刻**的环境块，新 PATH 要重开进程才生效 | 没提这一层（只在 7.18 提过） |
| 插件页装插件报 `pnpm not found on PATH`（退出码 127） | pnpm 没装，或者装到了另一个 Node 版本目录里                                 | 一键装 pnpm（这条已有）      |
| 想换 Node / pnpm 版本，只能自己去命令行               | 没有「更新」这个入口                                                        | 没有                         |

四个目标（就是用户那四句话）：

- **G1 开箱可判**：打开应用就能看出这台机器能不能跑，不能跑要说清缺什么；
- **G2 缺 Node 一键可装**：给按钮，两条路（官方直装 / nvm），不要把人支使到下载页去自己挑文件；
- **G3 环境 OK 才放行**：硬门禁拦住主界面，逐步引导到「够用」，同时**永远留一个逃生口**；
- **G4 版本可更新**：进了界面之后，能更新 Node 与 pnpm 的版本。

新增的每一样东西**只许接在四个既有形状上**，不许平行长出一套：

- **`EnvCheck`（与 `EnvCheckId` / `EnvCheckStatus`）**：门禁与三个步骤的全部事实来源。步骤判据就是读那几个既有 id 的 `status`，界面显示的就是既有的 `detail` / `fixHint`。**不新增探测项**，也就不新增「第二个事实来源」。
- **`EnvFixPlan`**：确认区的形状。新通道复用它「命令原文 + 目标 + note + 只递选择」的约定（阶段一 3.2 第 1 条），只是多几个字段（下载源、校验依据、要不要提权）。
- **`EnvFixState`**：跑一个动作时的状态形状（相位 / 消息 / 退出码 / 复检报告）。安装通道**同构但不同型**（多了下载与校验、取消语义相反），照它的结构写，不照它的语义用。
- **`LaunchSpec` / `launchSpec()` / `dshLaunchSpec()`（`src/main/process-utils.ts`）**：Windows 上起一切外部程序的唯一包装。安装器、nvm、npm 全部经它，**新代码不许直 spawn `.cmd` / 批处理、不许出现 `shell: true`**。

### 2.3 阶段一的两个决定，这次被用户明确推翻

必须显式记下来，否则两份文档会互相矛盾（`docs/env-doctor.md` 的 1.1 / 3.1 / 9 节、`src/shared/ipc.ts` 里 `EnvFixAction` 上方的注释、`README.md` 的「使用前提」都写着反过来的话）：

| 阶段一的决定                                                                                                  | 阶段二改成                                                            | 为什么                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 「不做一键装 Node」（`env-doctor.md` 1.1：装 Node 要系统级安装 / 改 PATH / 可能要管理员权限，失败面大于收益） | **做**：Node 必须有两条一键路径（第 7 节）                            | 用户的直接诉求是「一个纯净的电脑也能方便地使用」；把用户支使到下载页挑 msi 就是这个诉求的反面                                     |
| 「不提权、不改 PATH」（`env-doctor.md` 3.1 与 9）                                                             | **官方直装这条路径会提权**（由安装器自己触发 UAC）；**仍然不改 PATH** | 提权是安装官方 MSI 的必然结果，不是我们的选择；而「改 PATH」这件事我们**依然不做**（让安装器做），我们只**重读**系统里已有的 PATH |

仍然不变的三条（阶段一的价值观，阶段二继续守）：

1. **探测是只读的**：任何写盘 / 起安装器都发生在用户点了确认之后，且属于「安装」这条新通道；
2. **每次动系统之前都要用户看得到计划并确认**（命令原文 / 下载源 / 会改什么 / 要不要提权）；
3. **能自己做的一步就替用户做，但绝不替用户决定**（不静默装、不静默提权、不静默换源）。

## 3. 术语：内部名与用户语言

界面上的文案用**用户语言**；内部术语不许漏到界面上。这张表是两边的对照，也是 review 时的核对清单。

| 内部名（代码 / 文档）              | 界面上怎么说                                                                                                                                                                                                                                                         | 备注                                                                             |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 门禁 / `gate` / `blocked`          | 「运行环境还没准备好」                                                                                                                                                                                                                                               | 界面上一律不出现「门禁」两个字                                                   |
| 逃生口 / `escape`                  | 「先进入界面（环境还没准备好，我稍后自己处理）」                                                                                                                                                                                                                     | 这是用户自己做的决定，不是一个错误                                               |
| `EnvCheckId` / 自检项              | 具体名字：`外部 Node`、`Node 版本`、`npm`、`pnpm`、`dsh 本体`……                                                                                                                                                                                                      | 阶段一已有这套标题映射，沿用                                                     |
| `EnvFixPlan` / `plan`              | 「将要执行」+ 命令原文 + 「会装进：<目录>」                                                                                                                                                                                                                          | 只在用户点开确认区之后出现                                                       |
| 下载源 / `source`                  | 「下载来源：<主机名>」                                                                                                                                                                                                                                               | 显示主机名即可，不要显示完整长 URL（详情里给全文）                               |
| 校验 / `sha256`                    | 「已校验安装包完整性」；详情里给「校验依据：官方发布的校验清单」                                                                                                                                                                                                     | 不把哈希值塞进正文（太长），详情可复制                                           |
| 签名 / `signer` / `releaseSigning` | 计划阶段的未签名确认**只**由发布元数据的自述（`releaseSigning === 'unsigned'`）触发：「这个安装包没有数字签名，要装吗？」；下载后真的读到未签名 / 签名无效时才说「这个安装包没有数字签名」；读到有效签名说「签名者：<发行方>」；读不到就说「这次没能读到安装包签名」 | **计划阶段不许因为 `signer` 为空就说任何一句关于签名的话**（那时还没读，见 7.3） |
| UAC / 提权                         | 「接下来 Windows 会问你一次是否允许安装（管理员权限）」                                                                                                                                                                                                              | 不写「UAC」「提权」「runas」                                                     |
| PATH / 环境变量                    | 「系统查找路径」；详情里才出现变量名 `Path`                                                                                                                                                                                                                          | 不写「PATH」这个词给用户看                                                       |
| nvm / NVM_HOME / NVM_SYMLINK       | 「版本管理器（nvm）」；详情里才出现变量名                                                                                                                                                                                                                            | 不写 `NVM_SYMLINK` 到正文                                                        |
| `msiexec` / 退出码                 | 「安装程序」「安装没能完成（编号 N）」                                                                                                                                                                                                                               | 编号可以给（用来报障），但要让一句话在前                                         |
| 可跳过 / `skip`                    | 「这一步先跳过」+ 后果一句                                                                                                                                                                                                                                           | 跳过是知情选择，要写清后果                                                       |

| 签名读不到             | 结果区（继续安装后）                 | 「这次没能读到安装包签名。」（如实说，不编原因）                                                                                                                  |
| 拒绝提权               | 本步的结果                           | 「你拒绝了管理员权限，这台电脑上什么都没改。」+ 旁边给出「改用不用管理员权限的方式安装」                                                                          |
| 提权等待太久           | 本步的结果                           | 「我们不等了：安装可能还在后台进行，请按它自己的提示装完，装完点『重新检测』。」                                                                                  |
| 装好了                 | 本步的结果（成功后）                 | 「Node.js `<版本>` 装好了，这一项已经变成『正常』。」                                                                                                             |
| 别处要重开             | 本步的结果（成功后）                 | 「其它已经打开的终端窗口需要重开一次，才会用上新装的 Node。」                                                                                                     |
| 更新入口               | 自检页 `node` / `pnpm` 行            | 「更新 Node.js」/「更新 pnpm」                                                                                                                                    |
| 已经最新               | 自检页那一行的按钮态                 | 「已经是最新版（`<版本>`）」                                                                                                                                      |
| 更新完成               | 自检页那一行 / 结果区                | 「Node.js：`<旧版本>` → `<新版本>`。」/「pnpm：`<旧版本>` → `<新版本>`。」                                                                                        |
| 更新要先停 dsh         | 更新前的确认区                       | 「更新会先停掉正在运行的 dsh，更新完再问你要不要重新启动它。」                                                                                                    |
| 更新影响别的程序       | 更新前的确认区                       | 「这台电脑上可能还有别的程序在用这个 Node。」                                                                                                                     |
| 网络不通               | 失败结果                             | 「下载没成功（连接超时）。你可以：① 用浏览器打开下载页自己装 ② 换一个下载源 ③ 装好后点『重新检测』。」                                                            |
| 测不出来               | 主界面常驻横幅 / 向导里              | 「这一轮没测全（原因：`<原因>`），下面的结论可能不准。」                                                                                                          |
| 逃生口                 | 门禁层底部常驻按钮                   | 「先进入界面（环境还没准备好，我稍后自己处理）」                                                                                                                  |
| 逃生之后               | 主界面常驻横幅（不可关闭）           | 「运行环境还没准备好：`<第一步没完成的>`」+「继续配置」                                                                                                           |
| 回到向导               | 自检页顶部按钮                       | 「重新打开环境向导」                                                                                                                                              |

## 4. 「环境 OK」的判定：必须是一个纯函数

这是整份需求的**技术核心**：门禁不能靠界面上的 if 拼，必须落到一个纯函数上，这样自检与反例脚本才能在没有任何安装、没有 Electron 的环境里把它测完（沿用 `docs/env-doctor.md` 第 2 节定下的规矩）。

### 4.1 三个引导步骤（用户原话的「逐步引导」）

步骤只做三档，把阶段一既有的自检项**分组**，不新增事实来源：

| #   | 步骤（界面上的标题） | 完成判据（只读报告，纯函数）                                 | 用到哪几项既有自检            | 可以跳过吗 |
| --- | -------------------- | ------------------------------------------------------------ | ----------------------------- | ---------- |
| 1   | 安装 Node.js         | `node.status !== 'missing'`                                  | `node`、`node-version`、`npm` | **不可以** |
| 2   | 安装 pnpm            | `pnpm.status !== 'missing'`                                  | `pnpm`                        | **可以**   |
| 3   | 安装 dsh             | `dsh.status !== 'missing'` 且 `dsh-run.status !== 'missing'` | `dsh`、`dsh-run`              | **不可以** |

每条判据的「为什么」都沿用阶段一的既有结论，不许在这里另立一套：

- 步骤 1 判据**不含版本区间**：`node-version` 在区间外只是 `warn`（`docs/env-doctor.md` 1.2：那句区间是构建期要求，dsh 到底能不能跑由实测决定）。所以「Node 版本不在区间里」**不挡门禁**，只在步骤里加一句说明；真正能不能跑由步骤 3 的 `dsh-run` 说了算。判定用的区间文本一律取报告里的 `nodeRange`（单一来源），向导里**不许**再写一句版本区间。
- 步骤 1 判据**不含 npm**：npm 缺失只决定「一键动作能不能出现」（`envFixPlan()` 在没有 npm 时返回 `null`，阶段一 1.3 / 3.1），不是「环境行不行」的判据。它显示在步骤 1 的展开详情里，并给出 `corepack enable pnpm` 这条替代出路。
- 步骤 2 判据的口径是**「有输出才算可用」**（阶段一 1.4）：`pnpm` 那一项的 `missing` **包括**「文件在盘上、`pnpm -v` 却跑不出东西」这一种，所以「装完了但还是跑不起来」**仍然算待办**。收尾那条链（刷新查找路径 → 复检 → `<pnpm> -v` 功能实测）与失败诊断的形状见 `docs/env-doctor.md` 3.4。
- 步骤 3 判据**两个都要**：`dsh` 是「找得到」，`dsh-run` 是「实测跑得动」。dsh 的 CLI 在版本不兼容的 Node 上是静默退出（退出码 0、零输出，AGENTS 7.4），只看「找得到」会放行一台其实跑不动的机器。
- `dsh` 为 `warn`（走 `npx -y`）**算完成**：能用，只是每次要联网解析（阶段一 1.5 的判定）。门禁不该因为它慢就挡住用户。
- `bundled-runtime` 与 `shell` **不进入步骤**：它们不是「能不能用这台机器跑 dsh」的判据。它们照旧显示在环境自检页，门禁层里以一行「另外还有 N 项提醒（可稍后处理）」链到自检页。

### 4.2 三个步骤各自还有一个「测不出来」态

除了「完成 / 待办」，步骤还有第三种状态：**测不出来**。规则是纯函数的一部分：

> 一个步骤的判据不满足时 —— 如果它用到的自检项里**至少有一项是 `missing`**，这个步骤是 `todo`（明确缺东西）；如果**一项 `missing` 都没有**（只有 `warn`），这个步骤是 `unknown`（我们这一轮测不出来，不是用户缺东西）。

`warn` 的语义在阶段一里就是「能用但有隐患，或者这一轮没法确定（例如运行环境不允许起子进程）」（`EnvCheckStatus` 的注释）。把 `warn` 当成「缺东西」会造出一类最糟的体验：**我们的探测失灵，却把用户关在门外**（受限沙箱、企业策略拦子进程、杀软拦 spawn 都会撞上）。

### 4.3 门禁三态

| 门禁状态  | 什么时候成立（纯函数）                           | 界面行为                                                |
| --------- | ------------------------------------------------ | ------------------------------------------------------- |
| `blocked` | 至少有一个步骤是 `todo`                          | 盖住主界面，显示向导；逃生口可见                        |
| `unknown` | 没有 `todo`，但至少有一个 `unknown`              | **放行**，进主界面 + 常驻黄条「这一轮没测全」+ 向导入口 |
| `open`    | 没有 `todo` 也没有 `unknown`（全是完成或已跳过） | 放行，无额外提示                                        |

**跳过**只对「可以跳过」的步骤生效，而且**打在纯函数里**：

- 传进来的跳过集合里出现不可跳过的步骤 id（Node / dsh）时，**该 id 被忽略**（不是报错、也不是生效）。这条要有反例：把 `node` 塞进跳过集合，判定结果必须还是 `blocked` —— 这是「硬门禁」的兜底，防止将来有人在界面或设置里绕过去。
- 跳过只把该步骤从 `todo` 变成 `skipped`（界面显示「已跳过」），不改变任何探测事实。

### 4.4 期望的形状（签名与字段的最终稿在冻结设计时定）

```ts
/** 引导步骤的 id。数组顺序 = 界面顺序 = 用户要走的顺序 */
export type EnvWizardStepId = 'node' | 'pnpm' | 'dsh';

/** 一个步骤的状态。`unknown` = 这一轮测不出来（不是用户缺东西） */
export type EnvStepStatus = 'done' | 'todo' | 'skipped' | 'unknown';

export type EnvGateState = 'open' | 'blocked' | 'unknown';

export interface EnvWizardStep {
  id: EnvWizardStepId;
  status: EnvStepStatus;
  /** 判据那句话（人话，带事实：路径 / 版本 / 为什么），界面直接显示 */
  detail: string;
  /** 这一步用到了哪几项既有自检（界面用它做「展开看详情」的链接） */
  checkIds: EnvCheckId[];
  /** 不可跳过的步骤这里恒为 false，界面据此不给「跳过」按钮 */
  skippable: boolean;
  /** 能不能用既有的两个动作替用户做（pnpm / dsh 两步会给；Node 这一步走安装通道，这里恒为 null） */
  fixAction: EnvFixAction | null;
}

export interface EnvWizardState {
  /** 步骤判据读的那份报告（就是阶段一的报告，不复制一份） */
  report: EnvDoctorReport;
  steps: EnvWizardStep[];
  gate: EnvGateState;
  /** 为什么是这个门禁状态（blocked / unknown 时非空，open 时为 null） */
  gateReason: string | null;
  /** 用户已经跳过的步骤（来自设置）；只可能是可跳过的那些 */
  skips: EnvWizardStepId[];
}

/** 纯函数：不碰磁盘、不起子进程、不读 process.*、不看时钟（与 judgeEnvironment 同款约束） */
export function judgeWizard(report: EnvDoctorReport, skips: EnvWizardStepId[]): EnvWizardState;
```

**可离线验证的硬约束**（照抄阶段一 2 的写法）：`judgeWizard` 只读入参；所有 IO 在采集侧（`collectEnvProbe()`）与安装通道里。自检只要喂一个手工构造的报告字面量就能把三态 × 三步骤 × 跳过 × 不可跳过 的全部分支测完。

## 5. 入口门禁：拦住什么、什么时候、怎么放行、怎么离开

### 5.1 拦住的是什么

**拦住的是「主界面」这一个整体**：左栏、顶栏以下的九个页面、状态栏 —— 与启动锁盖住的区域一致（`index.html` 的 `#boot-lock`，AGENTS 7.9）。不锁顶栏，窗口能拖动、能关闭。

**门禁层不能做成左栏的第 10 个页面**：做成页面就可以用 `Ctrl+2` 切走，硬门禁就没有意义了。所以它是一个覆盖层，与启动锁同一种形态。

### 5.2 什么时候判定、拦住哪些状态

| 时机                     | 做什么                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| 应用启动（渲染层挂载后） | 先按阶段一的方式 `envCheck()` 拉一份报告（有缓存立刻给），再 `judgeWizard()` 判定 → 决定显示门禁层还是主界面 |
| 门禁层里每完成一步       | 主进程自动复检（沿用阶段一 3.3 的「跑完自动复检」），复检结果回来后重算步骤与门禁                            |
| 用户点「重新检测」       | 重跑一轮并重算（`refresh: true`）                                                                            |
| 运行中环境变化           | **不再上锁**（见 5.5 的单向规则）；只更新横幅与环境自检页                                                    |
| 下一次启动               | 重新判定（逃生口不写盘，所以逃走过一次不等于以后都不挡）                                                     |

**必须先探测、再决定要不要拉起 dsh**：纯净机器上自动拉起 dsh 必然失败，用户会先被启动锁盖住一段时间（启动锁最长 `BOOT_LOCK_MAX_MS`），然后才看到一堆红灯。所以顺序是硬要求：

```
启动 → 只读探测 → judgeWizard()
   ├─ blocked → 显示门禁层；**不自动拉起 dsh、不自动打开 Harness、不进全屏**
   ├─ unknown / open → 照旧走阶段一的自动启动流程（含启动锁）
   └─ 用户从逃生口离开 blocked → 进入主界面，并**此时**触发一次自动启动（若 autoStart 为真且本轮还没试过）
```

逃生口之后仍然走自动启动，是因为那时用户要的就是主界面（他可能是来看日志、来用本地 Shell 的），而启动锁自己也有逃生口（「不等了，先进入界面」），两者不冲突。

### 5.3 放行的判据

| 启动时判定的门禁状态 | 界面行为                                            |
| -------------------- | --------------------------------------------------- |
| `open`               | 不显示门禁层，直接进主界面（无额外提示）            |
| `unknown`            | 不显示门禁层，进主界面 + 常驻黄条 + 向导入口        |
| `blocked`            | 显示门禁层；唯一能点的「前进」是逃生口（第 5.4 节） |

**在向导里把环境弄好之后**（`blocked` → `open` 或 `unknown`）：门禁层**原地变成结果页**，出现「进入 DSH Console」按钮，**不自动跳走**。理由有两个 —— 修复输出与复检结论要让人读得完；用户可能还想在向导里多看一眼。这条也是「不替用户决定」的一部分。

注意 `unknown` 也允许进入（第 4.3 节）：门禁**只对「有证据的缺失」上锁**，我们自己的探测失灵不该变成用户的牢门。

### 5.4 逃生口：文案与语义

| 项     | 内容                                                                                                                             |
| ------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 位置   | 门禁层底部，**常驻**（不是超时后才出现、不是二级菜单里）                                                                         |
| 文案   | 「先进入界面（环境还没准备好，我稍后自己处理）」                                                                                 |
| 语义   | 放弃这一轮的门禁，进入主界面；**不做任何修改、不写盘、不改变判定**                                                               |
| 可达性 | **检查中也能点**（探测还没回来时也要能点，否则「我们的探测卡住」＝「用户被关住」）；修复动作正在跑时也能点；探测整体失败时也能点 |
| 后果   | 主界面出现常驻横幅（第 5.5 节），环境自检页顶部出现「重新打开环境向导」                                                          |
| 不写盘 | 逃生只存在于本次运行的内存状态里；**不是设置项**、不落任何文件（自检要钉住这一点）                                               |
| 可重复 | 从向导里逃生 → 回到向导 → 再逃生，永远有效；逃生不是一次性的豁免                                                                 |

### 5.5 单向规则与「回到向导」

照抄启动锁在 AGENTS 7.9 里踩过的那条教训：**用单向状态机，不要用「每次状态变化重新判定」的布尔量**。否则修好环境 → 用户手动做了别的 → 条件又变回去 → 门禁重新扣上来。

```
idle → checking → (blocked | released | escaped) → done
```

`done` 之后本轮的判定不再改变门禁（探测照旧重跑、旗帜照旧更新，但**界面不会被切走**）。这也是「硬门禁」与「骚扰」的分界：**门禁只在启动时施加一次**。

逃生之后回到向导，至少这三条路（都要有，缺一条就会有用户找不回来）：

1. **控制台页横幅**：不可关闭的一条横幅（沿用控制台页那条 `.banner` 的形状与位置），写「运行环境还没准备好：<第一步没完成的>」+「继续配置」按钮 → 重新显示门禁层；
2. **环境自检页顶部**：「重新打开环境向导」按钮（门禁层怎么进都不写盘，所以这个按钮只是把覆盖层再显示出来）；
3. **状态下不再需要横幅时自动消失**：用户在界面里自己把环境修好了（例如去命令行装了 Node），点一次「重新检测」后门禁变 `open`，横幅自己消失（判据来自报告，不是来自「向导走完过没有」）。

## 6. 逐步引导：每一步长什么样、怎么算完成、什么能跳过

### 6.1 步骤清单

| #   | 步骤         | 完成判据      | 一步能做什么                                                                                                                                                                                | 可跳过 | 跳过之后                                                                               |
| --- | ------------ | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | -------------------------------------------------------------------------------------- |
| 1   | 安装 Node.js | 第 4.1 节表格 | 两条路径二选一（第 7 节）；**版本管理器已装但它一个版本都没有时，由应用自己装一个稳定版并切过去**（7.6）；或「打开官方下载页自己装」                                                        | 否     | —                                                                                      |
| 2   | 安装 pnpm    | 第 4.1 节表格 | 一键安装（**就是阶段一的 `install-pnpm` 动作**：`<npmPath> i -g <pnpm 规格> --allow-scripts=pnpm`，装完当场实测能不能跑，见 `docs/env-doctor.md` 3.4）；npm 缺失时给 `corepack enable pnpm` | **是** | 「已跳过」标记保留在自检页与横幅里；插件页的装 / 卸 / 升级仍不可用，插件页那条提示照旧 |
| 3   | 安装 dsh     | 第 4.1 节表格 | 一键 `npm i -g @deepseek-ai/dsh`（**就是阶段一的 `install-dsh` 动作**）；`dsh-run` 不过时给「换一个 Node」的出路                                                                            | 否     | —                                                                                      |

跳过的**持久化**：跳过集合记在设置里（它是一个内部标记，不是给用户调的开关，形状与既有的 `trayHintShown` 同类），所以一次知情选择不会每次启动都重问。必须同时有「取消跳过 / 恢复引导」的入口（就放在环境自检页被跳过的那一行上），否则用户被自己的选择困住。

### 6.2 每一步都要有的四件东西

沿用阶段一环境自检页已经定下的交互形状（页内确认、不弹原生对话框、AGENTS 7.19），每一步都要有：

1. **为什么**：一句话说清这一步不做会怎样（「没有 pnpm，插件页的装 / 卸 / 升级都用不了」）；
2. **确认区**：将要执行什么（命令原文或安装器名）、下载来源（主机名）、会改到哪里、需不需要管理员权限、要不要联网。**必须用户点「开始」才动系统**；
3. **过程可见**：流式输出（沿用 `EnvFixOutputEvent` 的形状）+ 进度（下载时给百分比，复用 `UpdateState.percent` 那种做法）+ 中止/不再等待的按钮（语义按第 7 节区分）；
4. **收尾结论 + 下一步**：跑完**先刷新查找路径、再复检**（链的形状见 `docs/env-doctor.md` 3.4），pnpm 那一步还要**功能实测**（`<pnpm> -v` 有输出才算完成，文件在盘上不算）→ 这一步变绿 → 出现下一步；失败则**不编原因**（沿用阶段一 `summarizeEnvFixFailure` 的口径：认得出就给归纳过的一句，认不出就给原文尾部）。

### 6.3 每一步的失败出路（都要写进确认区与失败文案）

| 步骤 | 失败                                                               | 出路                                                                                                                                    |
| ---- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 下载不通（超时 / DNS / 连接被重置）                                | ① 用浏览器打开官方下载页自己装（浏览器的代理设置往往能用）② 换一个下载源 ③ 装好后点「重新检测」                                         |
| 1    | 用户拒绝管理员权限                                                 | 「你拒绝了管理员权限，这台电脑上什么都没改」，留在本步；可改用 nvm 那条路（不需要管理员权限）                                           |
| 1    | 安装器报错                                                         | 原文尾部 + 归纳过的一句 + 「打开官方下载页」+「重新检测」                                                                               |

## 7. Node 的两条安装路径

### 7.1 一张表说清差别

| 项                 | 官方直装（MSI）                                                                                                                               | 通过 nvm-windows 安装                                                                                               |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 装的是什么         | 官方 `node-v<版本>-<arch>.msi`                                                                                                                | 先装 nvm（`nvm-<版本>-<arch>-setup.exe`），再用它装 Node                                                            |
| 装到哪             | 系统级（默认 `%ProgramFiles%\nodejs`）                                                                                                        | 用户级（v2 的社区版安装在用户目录；Node 版本在 nvm 自己的目录里）                                                   |
| 需要管理员权限     | **需要**（系统级安装 + 改机器 PATH；Windows 会自己弹一次提权）                                                                                | **不需要**（v2 起「安装与运行都不需要特殊权限」；安装器可能为注册事件源弹一次，**拒绝也不影响功能**）               |
| 用户能自己选的     | 目标版本（最新稳定版 / 最新当前版）与架构（跟着系统）                                                                                         | 目标版本；nvm 自己的镜像设置（我们不改它）                                                                          |
| 对现有 Node 的影响 | 覆盖升级同一个 Node，未受管的多版本会被换掉                                                                                                   | 不动系统里的 Node，多版本共存，用 `nvm use` 切换                                                                    |
| 装完要不要重开进程 | **应用自己不用**（既有的 Windows 兜底目录会找到 `%ProgramFiles%\nodejs`），但**别处已开的终端/程序要重开**（或我们替它重读系统 PATH，见 7.4） | **应用需要重读用户 PATH**（nvm 的目录写在用户环境变量与用户 PATH 里，我们的进程拿到的是启动那一刻的旧值），别处同理 |
| 适合谁             | 「我只要一个能用的 Node」                                                                                                                     | 「我要多个版本 / 不想动系统 / 没有管理员权限」                                                                      |

**架构选择**：跟着系统位宽（x64 / arm64）选。目标版本必须先在版本清单里确认它提供了对应架构的 Windows 安装包，再开始下载 —— 拿不到就不下载，直接给「打开官方下载页」。

> **⚠️ t29 读表提示（VM-14）**：右边一列第 1 行的「先装 nvm……再用它装 Node」是**机器上还没有版本管理器**时的形状。
> 机器上**已经有**一个可辨认的版本管理器时，我们**不再装它一遍** —— 直接 `nvm install <目标版本>` → `nvm use` → 复检（§7.8）。
> 另外：**这两条路不是让用户随便挑的**，走哪一条由"这份 Node 是谁管的"决定（§7.7 / §7.8）。

**不做便携 ZIP**（明确记在案）：官方也提供 `win-x64.zip`，解压即用、不需要管理员权限，但它**不写系统 PATH** —— 要么用户每次都要自己配，要么我们在自己的解析里开一个「私有 Node」的口子，于是 `findNodeExe()` 就出现了第二个事实来源，用户换 Node / 卸载 dsh 之后会出现两份互相矛盾的结论。这条路与「复用同一个启动形状」的既有约定相冲突，所以不做；真的想免安装的用户走 nvm 那条路。

### 7.2 官方直装：完整流程

1. **解析目标版本**：取 Node 官方的版本清单（`https://nodejs.org/dist/index.json`），**默认选最新稳定版**（清单里 `lts` 字段非 false 的第一条，通常是 LTS），另给一个「最新当前版」（清单第一条）作为可切换项。确认区要显示**具体版本号**与「这是哪一档」（稳定版 / 当前版），不许含糊地说「最新版」。**这份清单只用来列版本**（顺带给出 `npm` 版本号 —— npm 会随 Node 一起装好），**不用它判断有没有对应架构的安装包**：`index.json` 的 `files` 数组从来不列 `win-arm64-msi`（实测证据见 7.3），拿它当判据会让 arm64 机器永远拿不到这个功能。
2. **判定「这个版本在这台电脑的架构上有没有安装包」——权威来源是同一版本目录下的 `SHASUMS256.txt`**（我们为了校验哈希本来就要取它）：`node-v<版本>-<arch>.msi` 出现在清单里才算存在，哈希也直接从这里取。**取不到清单时就如实报网络失败**（出路是换一个下载源 / 官方下载页 / 重新检测），**不许**降级成「这个版本没有适合这台电脑的安装包」——那是在替官方下一个我们没验证过的结论。
3. **确认区**：安装包名与版本、下载来源主机名、需要管理员权限（一句用户语言）、会装到哪里、会改什么（新增/覆盖系统里的 Node）、以及「窗口会弹一次询问是否允许安装」。**确认区里的风险说明不包含任何关于签名的断言**（那时还没读到签名，见 7.3 第 2 条）。
4. **下载**：下到用户数据目录下的一个临时目录（不要写到桌面或系统目录）。下载过程给百分比，**下载可以取消**（取消只删临时文件，系统没有任何改动）。
5. **校验与读签名**（见 7.3）：先比哈希 —— 与清单不一致就**不安装**；再读安装包的数字签名 —— 读到有效签名就记录签名者，读到**明确未签名 / 签名无效**就不安装（给「打开官方下载页」的出路），读不到 / 结论不明确就继续安装、并在结果里如实写「这次没能读到安装包签名」。
6. **安装**：运行安装包，走 **Windows 会自己弹的那次提权询问**。确认区里已经预告过；用户拒绝 / 取消 / 等太久的三种结果按第 9.2 节分别处理。
7. **复检前先重读 PATH**（见 7.4），再自动复检一次；复检结果决定这一步是完成还是仍待办。

### 7.3 完整性证据：可校验、写在界面上、不硬编码

| 路径        | 下载来源                                                                                                                                              | 可校验的完整性证据                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 官方直装    | `https://nodejs.org/dist/v<版本>/node-v<版本>-<arch>.msi`                                                                                             | ① 同一目录下的官方校验清单 `SHASUMS256.txt`：**它同时是架构存在性的判据**（见 7.2），下载后算 SHA-256 与清单里该文件那一行比对；② 清单本身有官方签名文件（`.sig` / `.asc`）可用于校验清单；③ 安装包是 Authenticode 签名的，下载后可以读取它的签名者与签名有效性（这是比哈希更强的「发行方身份」证据）                                                                                                |
| nvm-windows | 发布资产（社区版）：新线是两个名字 —— `nvm-<版本>-amd64-setup.exe` 与 `nvm-<版本>-arm64-setup.exe`；**旧线**是 `nvm-setup.exe`；`*-sync.exe` 一律跳过 | ① 发布 API 的每个资产可能带 `digest`（形如 `sha256:<值>`）：**新线（2.x）有，旧线（1.2.x）是 `none`** —— 旧线只提供 `nvm-setup.zip.checksum.txt`，它覆盖的是 zip、**不能用来猜 exe 的哈希**；② 发布说明里有机器可读的签名自述（`Authenticode-signed community build from …` 与 `Unsigned community build from …`），**这是计划阶段唯一能依据的签名事实**；③ 安装包下载后可以读它的 Authenticode 签名 |

**发布线的现状（必须写对，因为它决定默认路径长什么样；证据见 `docs/env-wizard-freeze.md` 的 R-27）**：`coreybutler/nvm-windows` 已改址到 `nvm-windows/nvm`（旧路径 **301** 到同一仓库），**最新稳定版 v2.0.0 标的是 `Unsigned`**（标 `signed` 的那个 `v2.0.1-hotfix.2` 是预发布）。所以「未签名要额外确认」在 nvm 那条路上是**今天的默认路径**，不是罕见情况 —— 文档与文案都不许把它写成边缘分支。

四条硬要求：

1. **不许把哈希值写进代码**（那会让每次 Node 发版都要改一次代码，而且一定会过期）：校验值必须**运行时取**。**取不到时的行为按路径分**（这一条在 t13 里改过，见 `docs/env-wizard-freeze.md` 的 R-25 / R-27 第 4 条）：
   - **官方直装**：哈希与「这台电脑的架构有没有安装包」都来自 `SHASUMS256.txt`。拿不到清单 → **不给「开始」**（计划照常给出来，只是 `usable: false` + 一句网络类原因），如实说「没能从官方来源拿到这个版本的校验清单。」+ 换源 / 官方下载页 / 重新检测。**没有"仍然继续"**（没有清单就判不了存在性，也校验不了）；**也不许**说成"这台电脑不支持"。
   - **nvm 的旧发布线**（没有 `digest`）：`sha256 === null` 是**正常情形** → 走既有的「**这次没能校验安装包的完整性。**」确认：**换一个下载源再试**（默认焦点） / **仍然继续**。**不许**拿 `nvm-setup.zip.checksum.txt` 去猜 exe 的哈希。
2. **签名的语义是分阶段的，而且要区分两个不同的事实**（这一条在 t13 里被真机事实改过一次，见 `docs/env-wizard-freeze.md` 的 R-26 / R-27）：
   - **计划阶段**：`signer` 为 `null` 只表示「**尚未读取**」（Authenticode 要读文件才拿得到）。界面**不得**据此显示「没有数字签名」、**不得**因此多一次确认；风险说明只写中性陈述（「下载后校验 SHA-256 与官方清单，并读取数字签名；不一致就不安装」）。
   - **计划阶段唯一能依据的签名事实是「发布元数据的自述」**，它以 `EnvNodePlan.releaseSigning`（`'signed' | 'unsigned' | 'unknown'`）表达：官方直装**恒为 `'unknown'`**；nvm 那条路按发布说明里的自述解析，认不出来是 `'unknown'`（**不许猜**）。**只有 `releaseSigning === 'unsigned'` 才在计划阶段出现**那句确认「这个安装包没有数字签名，要装吗？」（默认焦点给「取消」）。
   - **下载后**（真的读到结果才说话）：读到有效签名 → 记录签名者并继续；读到**明确未签名 / 签名无效** → **如果 `releaseSigning === 'unsigned'`（用户已经在计划阶段确认过）就继续**，否则**不安装** + 「打开官方下载页」的出路（官方包里出现这个状态是红 flag）；**读取失败 / 结论不明确** → 继续安装，但在结果里如实写「这次没能读到安装包签名」。
3. **来源可切换，但不静默切换**：下载源留一个设置项（默认官方直连）。换源意味着信任另一台主机，所以**必须由用户操作触发**，且确认区要显示当前用的是哪个源。文档里可以举例说明「国内常用镜像」，但**代码里不硬编码镜像、也不默认换源**。**注意这个源只对 Node 的安装包生效**：版本管理器的安装包来自 GitHub 的发布资产（没有镜像语义），走 nvm 路径时确认区要写明「版本管理器的安装包仍然从官方地址下载」。
4. **两边都要能"照实说"**：我们拿不到校验值 / 读不到签名时，说的是「没能拿到 / 没能读到」，**不许**说成「没有数字签名」（那是结论，要有证据）或「这台机器不支持」（那是官方的结论，不是我们的）。

### 7.4 装完怎么才能立刻认出新 Node（Windows 上的关键一步）

事实（既有代码就说清了这件事）：Windows 上 GUI 应用拿到的是**启动那一刻**的环境块，「刚装完还没重新登录时，终端里能用、应用里找不到」（AGENTS 7.18 第 2 条、`process-utils.ts` 的 `windowsBinCandidates` 注释）。

两条路径的差别是硬的：

- **官方直装（MSI，装到默认位置）**：既有解析兜底已经覆盖了 `%ProgramFiles%\nodejs`（`windowsBinCandidates` 里的候选目录），所以**应用自己不用重开**就能复检到新的 node / npm。
- **nvm 路径**：nvm 把 node 放在自己的目录里，并且把目录写在**用户环境变量与用户 PATH** 里；既有的 Windows 候选目录里只有「版本管理器的软链/符号目录」这一项，**没有** nvm 的各版本目录。所以刚装完 nvm、还没重开应用时，既有解析**认不出来**。
  > **⚠️ 这段的 v1 前提已被真机推翻（见 7.6）**：nvm-windows **v2** **不设** `NVM_HOME` / `NVM_SYMLINK`，用户 PATH 里是 `<root>` 与 `<root>\.nodejs`、各版本在 `<root>\installs`。所以别再按「软链 / 符号目录」去找它 —— 判据已改成**按真实证据推模型**（`deriveNvmModel`），`windowsBinCandidates` 也从 PATH 里那条 `<root>\nvm` 推出 `<root>\.nodejs`。下面「重读系统环境」这个结论不变，只是**读什么**跟着 7.6 走。

所以安装通道里必须有一个明确的一步：**从系统里重读环境（用户级 + 机器级的环境变量与 PATH），把结果并进我们给子进程用的那份环境**。这样两条路径装完都能立刻复检通过，用户不必重开应用。要点：

- 只读系统里已有的 PATH 并**合并**，不去**改**系统 PATH（「不改 PATH」这条不变量继续成立）；
- 合并逻辑要能用纯函数测（例如「把注册表里读到的两段 PATH 合成一段、保留原有键名、去重、顺序稳定」这件事本身是纯函数，读注册表是 IO）；
- 界面上仍然要提示一句「**其它已经打开的终端窗口要重开一次**才能用上新装的 Node」—— 我们只能刷新自己，别人家的进程我们管不了；
- 复检仍然走阶段一的 `envCheck({ refresh: true })`，不另造一条探测路径。

### 7.5 已经装过 nvm 的机器

如果机器上已经有 nvm（能从系统里读到 nvm 自己写的环境变量，或找到了它的可执行文件），那么：

- ~~向导的 Node 一步默认选 nvm 那条路~~ —— **本轮有意不做**：要按"这台机器上有没有 nvm"改默认，需要**一次新的探测 + 一个契约字段**；本轮两条路都默认「直接安装官方版本」，用户自己在选单里选 nvm（「支持选择直接装或经 nvm 装」这个需求已经满足）。理由：在一个已经有 nvm 的机器上多花一次探测与一个契约字段，换来的只是"少点一次单选框"，不划算；而**误覆盖**的风险由用户自己选、并且确认区会写清"会覆盖现有的 Node"来兜住。

> **⚠️ t29 标注（VM-14 / VM-15）：上面这一条「本轮有意不做」被推翻 —— 现在做。** 真机实测证明，"两条路都默认直装、由用户自己选"
> 这个前提是不成立的：用户在**已被版本管理器管的机器**上点「更新 Node.js」，界面把方法写死成直装，
> 于是它真的去装了一份官方 MSI 到 `C:\Program Files\nodejs`（见 §7.7 / §7.9）。
> 现在**归属是判出来的事实**（§7.7）、**方法跟随归属**（§7.8）、默认档位跟随当前档位（§8.5），
> 契约增量在 §11.2.1（冻结文档 §0.2 记这次推翻）。**上面那段原文保留**，作为"为什么会走到这一步"的历史。

- 反过来，如果系统里已经有一个非 nvm 的 Node，且用户选了 nvm 这条路，确认区要写清「这台电脑上原来的 Node 不会被删掉；之后 `node` 走哪个要看谁在系统查找路径里靠前」—— 这句必须说，否则用户会遇到「装完了但用的还是旧的那个」。
- **已经装好版本管理器、但它一个 Node 版本都没有**（客机的真实状态）：这一种不是"让用户自己去选一个版本"，而是**由应用自己装** —— 模型、状态文案与那条完整链路见 7.6。

### 7.6 版本管理器的真实模型（v2 实证）与「管理器在、零版本」

**为什么要有这一节**：7.4 / 7.5 里关于 nvm 的假设是 **v1** 的形状（`NVM_HOME` 放版本、`NVM_SYMLINK` 是当前版本、PATH 里是那个软链）。VM-11 的客机（nvm-windows **v2.0.0**，程序根形如 `…\Author Software\nvm`）把这几条推翻了 —— 下一个人若按 v1 再写一遍，就会得到「装完了但应用找不到它」（那正是 VM-12）。所以模型以**真机证据**为准写在下面；`docs/env-wizard-freeze.md` §0.1 只留一行指针（**模型会跟着实现改，所以放这份设计文档；冻结文档只记「哪几条被推翻」**）。

**v2 的真实形状**（客机实测；`HKCU\Environment` 里只有 `Path` / `TEMP` / `TMP` / `OneDrive`，没有任何 `NVM_*`）：

| 项                 | v2（当前线）                                                      | v1（老线；只作兜底）                 |
| ------------------ | ----------------------------------------------------------------- | ------------------------------------ |
| 模式               | **shim**：`<root>\.nodejs\node.exe` 是把当前版本转发出去的 shim   | link：`NVM_SYMLINK` 指向当前版本目录 |
| 各版本装在哪       | `<root>\installs\<版本>`（注册表 `InstallRoot` / `nvm env` 同说） | `NVM_HOME` 下的各版本目录            |
| 当前的 Node 从哪来 | `<root>\.nodejs`（用户 PATH 里就有这一条）                        | `NVM_SYMLINK`                        |
| 环境变量           | **不设 `NVM_HOME` / `NVM_SYMLINK`**                               | 设这两个                             |
| 开关               | `nvm on` / `nvm off`（注册表偏好里的 `Enabled` 读得到）           | 没有这一对（或语义不同）             |
| 程序根             | 用户 PATH 里那条 `…\nvm`、或 `nvm.exe` 的真路径                   | `NVM_HOME`                           |

**我们据此怎么推（`deriveNvmModel`，纯函数、`exists` 可注入）**：证据优先级从高到低 ——
① `nvm.exe` 的**真实路径**（PATH 里找到的真文件）→ 根目录就是它的目录；
② `nvm env` 的报告 / 注册表偏好（`OperatingMode` / `InstallRoot` / `Enabled` / `ActiveVersion`）；
③ 用户级 PATH 里那条 `…\nvm`；
④ `NVM_HOME`（**只**作 v1 风格机器的兜底）。
`mode` 先信 `nvm env` 说的，没有就看磁盘（`<root>\.nodejs` 在 → `shim`，`NVM_SYMLINK` 在 → `link`）；
`activeDir` 先认 PATH 里真实存在 `node.exe` 的 `.nodejs`，再看 `NVM_SYMLINK` 与 `<root>\nodejs`；
`installsDir` 取 `nvm env` / 注册表的 `InstallRoot`，退到 `<root>\installs`。每条结论都进 `evidence`（进日志，评审时能对账）。
**v1 风格的机器不被排斥**：真有 `NVM_HOME` / `NVM_SYMLINK` 就按真的来（`Nvm_Home` / `Nvm_Symlink` 两种写法都认）。

**「管理器在、零版本」这个状态**（客机就是这一台）：版本管理器装好了，但它一个 Node 版本都没有
（`nvm list` → `No versions installed.` / `No installations recognized.`），于是 `<root>\.nodejs\node.exe` 这个 shim
跑起来**零输出**，它自己的原文是 `No active Node.js version is configured. Run \`nvm install <version>\` then \`nvm use <version>\`.`

| 谁                           | 说什么 / 做什么                                                                                                                                                                                                                                                                                                                  |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 环境自检的 `node-version` 行 | `missing`，`detail` **说中这一种状态**：「版本管理器已经装好了：这份 Node（…\.nodejs\node.exe）就在它管的目录里，但它还没有装任何 Node 版本（或者没有选中一个），所以这个 node.exe 现在跑起来没有任何输出」；`fixHint` 第一句是应用内那条路「点上面的『安装 Node.js』…都由我们装好并切过去」，命令行只作"想自己来也可以"的备选   |
| 门禁                         | `blocked`、`currentStepId = node`（有证据的缺失就挡，判据见 4.1）                                                                                                                                                                                                                                                                |
| 应用**自己**做的那一步       | 挑一个稳定版（官方清单里第一条 `lts !== false`）→ `nvm install <版本>`（看退出码 + `Installed Node.js …` 标记）→ `nvm list` 核对清单里真出现了该版本 → `nvm use <版本>` → 实测 `<node> --version` 与 `<npm> --version` **都有输出**才算完成（`verifyActiveNode`；shim 那句 `No active Node.js version is configured…` 不算可用） |

**为什么必须由应用自己装**：那句 shim 原文是**把活推给用户**的话，而用户在门禁层里本来就是「来找应用帮忙」的。
这条与 VM-04 的「不许把内部记号暴露给用户」并列成界面文案的两条红线，**都由自检的行为断言守着**：
`test/selftest.ts` 的「环境自检（VM-13）」逐字钉住客机文案与词表扫描，`scripts/env-wizard-cases.mjs` 的
`looksVersionManagerNode`（N4c 不误判 `/nvm-tools/`）、模型推导（N6）与 N7b–N7e 钉住"应用内那句话 + 不许打发去终端"。

## 7.7 「这份 Node 是谁管的」：归属判定（VM-14 的根）

**为什么要有这一节**：更新 / 安装 Node 的**方法**必须跟着**这份 Node 的真实归属**走。VM-14 的现场是：
这台机器上的 Node 是版本管理器管的（`…\Author Software\nvm\installs\v26.9.0\node.exe`），而「更新」把方法写死成直装，
计划就成了 `msiexec /i node-v24.21.0-x64.msi` → `C:\Program Files\nodejs`。照它执行，这台机器上会有**两份 Node**
（并存本身的危害见 §7.9），而"现在这份 Node 用的是哪一份"只由系统查找路径里谁靠前决定。

**三个取值**（契约里叫 `EnvNodeOwner`，进 `EnvDoctorReport.nodeOwner`，见 §11.2.1）：

| 取值      | 判据（**任一条成立**即算这一条）                                                                                                                                                                                                                                          | 证据从哪来                                                                                                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `nvm`     | ① 路径落在**模型给出的**版本管理器目录下：v2 的 `<root>\installs\<版本>`、`<root>\.nodejs`（shim），v1 的 `NVM_SYMLINK`，或 `NVM_HOME` / `NVM_DIR` 下；② 路径里出现**独立的目录名** `nvm` / `nvm4w`（`D:\nvm-tools\node.exe` 这种带别的名字的不算 —— 沿用既有判据的写法） | §7.6 的 `deriveNvmModel`（`nvm.exe` 的**真实路径** → `nvm env` / 注册表偏好 → 用户 PATH 里那条 `…\nvm` → `NVM_HOME` 兜底）+ `NVM_HOME` / `NVM_SYMLINK` / `NVM_DIR` + 既有 `looksVersionManagerNode` 的目录名判据 |
| `system`  | 落在**官方安装包的默认安装位**：`%ProgramFiles%\nodejs`、`%ProgramFiles(x86)%\nodejs`，变量读不到时 `C:\Program Files\nodejs`；或落在**官方安装包自己写下的安装目录**下（`HKLM\SOFTWARE\Node.js` 的 `InstallPath`，读得到时才算）                                         | 自检报告里那份 Node 的**真实路径**（既有的 `findNodePath()`，就是 `node` / `node-version` 两行判据用的那个） + 那两个环境变量 + 上面那个注册表键（**读不到就不管这一条**，不影响结论）                           |
| `unknown` | **其余全部**：没找到 Node / 找到但认不出归谁 / 归**别的**版本管理器（volta / fnm / nvs / nodist / scoop —— 它们既不是 nvm，也不该被当成"系统装的那一份"）                                                                                                                 | ——                                                                                                                                                                                                               |

**三条定死的规矩**：

1. **判据只有一份，而且必须能被离线测**：它是个纯函数（入参是路径 + 环境变量 + §7.6 的模型结论，没有 IO、不抛），
   名字沿用既有的 `detectNodeOwner`（签名见冻结 §4.2 的 t29 标注）。**采集侧（`main/env-doctor.ts` 的完整探测与快速探测）
   与安装计划（`main/node-installer.ts`）都调它** —— 渲染层**不许**再写一份路径判断，安装引擎里也不许有第二份。
   方向是 `env-doctor → node-installer`（与既有"安装引擎不许 import env-doctor"正好相反），所以不构成环。
2. **快速探测也判得出来**：启动瞬间那一次只读文件系统与注册表（`nvm.exe` 的真实路径、用户 PATH 里的条目、`<root>\.nodejs` 在不在），
   **不起子进程** —— `nvm env` 只是加分证据，判据里没有一条依赖子进程（照 R-19 的边界）。
3. **`unknown` 时不猜**（VM-14 的核心裁定）：
   - **不许默默走直装**。"归属判不出来"等于"我们不知道该用哪种方式更新它"，默认值**不能**替用户做这个决定；
   - **更新**（`mode === 'update'`）：**不做自动更新**（沿用交互规格 §10.5 第 6 条，现在这条有了可实施的事实来源）。界面说
     **我们认不出这个 Node 是怎么装的，所以不会替它做自动更新。** 并给 **打开官方下载页** / **重新检测**；
   - **安装**（`mode === 'install'`，即要给这台机器弄一个能用的 Node）**分两种**：
     - **找到了一份 Node**（含归别的版本管理器）：**一条都不预选**，由用户**显式选**，并照实说我们不确定 + 两份并存的后果
       （原样文案见 §7.9 第 4 条）。这个状态写在 `EnvNodePlan.needChoice === 'choose-method'` 上，**界面不自己判"要不要问用户"**；
     - **一份 Node 都没找到**：这时没有"已被管理的 Node"可以被复制，所以给一条**有事实支撑的默认** ——
       模型推得出一个版本管理器 → **默认用它**（这就是 §7.5 当年"有意不做"的那条默认，现在有依据了）；
       推不出来 → **默认官方直装**（既有设计默认）。
       **但"有默认"既不等于"默默"，也不等于"不给选"（VM-16 修订）**：这两条路**都要列出来**让用户改
       （预选只是预选），而且这一步的**事实行**必须把**方法**说出来（不只是档位）：
       **这台电脑上还没有 Node：默认用官方安装包装到系统默认位置。也可以改用版本管理器（不用管理员权限、可以装多个版本）。**
       / **这台电脑上还没有 Node，但已经装了一个版本管理器（nvm）：默认用它装，之后可以随时切换版本。也可以改用官方安装包（会问一次管理员权限，装到系统默认位置）。**，
       确认区再固定一行重述（交互规格 §4.3 第 8 条）。
       > **VM-16 现场（真机实测）**：实现把"默认选中"做成了"只给一句事实行、另一条路点不了"——用户重置虚拟机后第一次装 Node，
       > 界面上**找不到「用版本管理器安装」**，只能走官方安装包。这与最初需求「**支持选择直接安装 node 或者通过 nvm 安装 node**」
       > 直接冲突，也让"第一次装的那台机器"失去了唯一一次选路的机会。修正后：**两条路都在，默认预选，随时能改。**
     > 这一条是**有意如此**（评审会问）：VM-14 的危害来自"**已被版本管理器管理的机器**上再装一份官方 Node"，
     > 而"这台机器上一份 Node 都没有、也没有版本管理器"不存在这个风险；把它也改成"必须显式选"，
     > 只会让最常见的那台机器（第一次装）多一次没有信息量的点击，而换不来任何安全。

## 7.8 方法跟随归属（安装与更新同一张表）

| 归属      | 方法                           | 怎么做                                                                                                                                                                                                                                                                           | 界面（交互规格 §4.1 / §4.3 / §10.5 落地）                                                                             |
| --------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `nvm`     | **必须是 `'nvm'`**             | **不装、不升级版本管理器本身**（它已经在机器上了，见下）→ `nvm install <目标版本>`（看退出码 + `Installed Node.js …` 标记）→ `nvm list` 核对清单里真有它 → `nvm use <目标版本>` → 实测 `<node> --version` 与 `<npm> --version` **都有输出**（§7.6 那条判据，「真的能跑」才算完） | 只有这一条路：**不出现**「直接安装官方版本」这个选项（它会在 `C:\Program Files\nodejs` 再放一份 Node）                |
| `system`  | **必须是 `'direct'`**          | 官方 `node-v<版本>-<arch>.msi`，走 §7.2 的完整流程（下载 → 校验 → 提权 → 安装 → 复检），**装回它自己的位置**                                                                                                                                                                     | 只有这一条路：**不出现**「用版本管理器安装」这个选项（它会另建一份 Node）                                             |
| `unknown` | **我们自己不定**（除一种情形） | 按 §7.7 第 3 条**分两种**：**找到了一份 Node** → 不预选（`needChoice: 'choose-method'`）；**一份都没找到** → 推得出模型就用它、推不出来就用官方直装（事实行必须写出方法）                                                                                                        | 找到了一份 Node：两条路都列、**一条都不预选**，用户显式选完才给「开始」；一份都没找到：显示事实行（方法写在那句话里） |

**「不装、不升级版本管理器本身」这条是硬的**（t29）：机器上已经有可辨认的版本管理器时，这次**没有任何东西要下载**。
既有实现是"先把版本管理器的安装包装一遍，再用它装 Node"，在"更新 Node"这条路上这是错的 —— 它把一次（不必要的）
版本管理器重装塞进了一次 Node 更新里（多几十 MB 下载、会重写它自己的偏好与 PATH 条目、确认区还会说"要下载版本管理器的安装包"）。
契约上用 `EnvNodePlan.installsManager` 表达（`false` = 跳过下载与校验两段，见 §11.2.1）。

**唯一的三个例外**（每一个都必须由用户**显式**点名，且确认区必须带上 §7.9 第 4 条那句并存风险）：

1. **归属未知**（上表第三行，`needChoice: 'choose-method'`）；
2. **归属 = `system`，但用户拒绝了管理员权限**（既有交互 §4.4 / §8.2 的替代出路「用版本管理器安装」）：
   直装装不下去，用户显式改走版本管理器 —— 我们会**新增**一份 Node（系统里那份不动），必须提前说清；
3. **归属 = `nvm`，但当前进程是提权态**（冻结 §1.2 R-23：nvm 社区版不许以管理员身份配置）：nvm 那条路 `usable: false`，
   替代出路是「直接安装官方版本」—— 同样要带并存风险。

**为什么默认不再允许"随便选一条"**：两条路对系统的改动完全不同（一个覆盖系统里那一份、一个只管版本管理器自己那份），
而"这台机器上现在这份 Node 归谁管"是**事实**，不是偏好 —— 事实能定的，就不该让用户凭猜去选。
**为什么不干脆把另一条路藏起来**：用户真的需要它时必须能走（没有管理员权限、或就是想要两份并存），
所以那三个例外留着，只是要求**显式 + 说清后果**。

## 7.9 两份 Node 并存为什么是坏的（VM-14）与我们的承诺

**会发生什么**：官方安装包装到 `%ProgramFiles%\nodejs` 并往机器 PATH 里加一条；版本管理器那份在它自己的目录里，
由它自己的用户 PATH 条目或 shim 生效。**两份都真实存在、都能跑**，于是"现在 `node` 是哪一份"只由**系统查找路径里谁靠前**决定 ——
而这件事会随安装顺序、登录方式（终端 / GUI）、甚至另一个安装器改了 PATH 而变化。

**为什么这是坏的，而不是"多一个也无所谓"**：

- **同一个应用的两个进程可能用不同的 Node**：GUI 进程拿到的是**启动那一刻**的环境块（§7.4），新开的终端读的是新的；
- **插件与本地 Shell 用哪一个不由我们决定**：它们各自从自己的 PATH 解析（`AGENTS` 7.18 的 `dsh plugin` 就是裸 `node` / `pnpm`）；
- **"更新成功了但没生效"会变成常态**：复检说"这台电脑上有一份能跑的 Node"，不等于**用户正在用的那一份**是新的；
- **排查成本高**：删掉一份之后另一份才浮出来，用户看到的现象会变两次，而我们没有任何界面能说清"你刚才用的是哪一份"。

**我们的承诺**（界面上说的话都从这四条来）：

1. **归属已知时不装第二份**：`nvm` 只走版本管理器、`system` 只走官方安装包（§7.8 那张表）；
2. **归属未知时不猜**：不做自动更新，或让用户显式选并说清后果（§7.7 第 3 条）；
3. **永不替用户改系统查找路径**（既有不变量：只**重读**、只**合进子进程**，不写系统 PATH，见 §7.4）；
4. **用户明确要求并存时，我们不拦，但必须先在确认区看到后果** —— 原样一句（同一句用在三个例外的确认区里）：

   > **这样这台电脑上会有两份 Node：一份是原来的（不会被删掉），一份是这次装的。之后 `node` 用哪一份，看系统查找路径里谁在前。**

   **⚠️ t7 标注（船长裁定；上面那句原文保留）——「原样一句」管的是哪一句**：它管的是**绑定的那句**，
   也就是**确认区渲染出来的** `EnvNodePlan.note` / `coexistWarning`（引擎里的常量 `NODE_COEXIST_WARNING`，
   `src/main/node-installer.ts`）—— 用户在做**有后果的动作**时看到的那一句，必须与引擎常量**逐字一致**。
   **选项标签允许改写**：同一件事在"两条路"的**选项说明**里可以换一种人话说（现在的措辞差异就在这一处）——

   | 位置                           | 说的是什么                                        | 归属                                                                |
   | ------------------------------ | ------------------------------------------------- | ------------------------------------------------------------------- |
   | `node-installer.ts` 的常量     | `…之后 `node` 用哪一份，看系统查找路径里谁在前。` | **绑定句**：确认区渲染它，逐字不许改                                |
   | `EnvGate.vue` 的 `METHOD_RISK` | `…之后哪一份生效，看系统查找路径里谁在前。`       | **选项标签 / 提示**：允许改写（措辞差异按此记录，**不需要改代码**） |

   （这是**记录**，不是要求把两处改成一样：边界是"**做有后果的动作时看到的那句**必须与引擎常量一致"，
   而选项标签只承担"选之前让人看懂"。要收紧到"连标签也逐字一致"是一次代码改动 —— **不在 t7 的范围里**。）

## 8. 版本更新（进入主界面之后）

### 8.1 入口

只在**环境自检页**（左栏第 8 项，`Ctrl+8` / `⌘8`，阶段一已有那一页）：

| 自检项 | 什么时候出现按钮 | 按钮文案           | 点下去是什么                                                                                                             |
| ------ | ---------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `node` | 找到了 Node 时   | 「更新 Node.js」   | 与第 7 节**同一条安装通道**，只是 `mode: 'update'`（前置与文案不同）                                                     |
| `pnpm` | pnpm 可用时      | 「更新 pnpm」      | **就是阶段一的 `install-pnpm` 动作**（对已装的就是升级；argv 与收尾判据见 `docs/env-doctor.md` 3.4），只换文案与出现条件 |
| 任一项 | 该项缺失时       | （不出现更新按钮） | 缺失时该行给的是「安装」，不是「更新」                                                                                   |

**不新增页面、不新增第二个安装实现**：更新与安装共用同一条通道（Node）与同一个动作（pnpm）。这条要在 review 里盯住 —— 一旦有人为「更新」另写一条 npm / 安装器路径，就会出现两处会漂移的失败归因。

**t29 修订（VM-14）：入口出不出现、动作叫什么，都由"归属 + 档位"算出来，不许在界面里写死**：

1. `nodeOwner === 'unknown'` 时**不出现「更新 Node.js」** —— 那一行给 **打开官方下载页** + **重新检测**，
   并把 §8.3 第 3 行那句"我们认不出这个 Node 是怎么装的，所以不会替它做自动更新。"写在行上（判据见 §7.7 第 3 条）。
   **VM-14 的直接成因就是这里没有看归属**（`EnvPane.vue` 把 `method: 'direct'` 写死）。
2. 动作名由计划决定：**同档** → 「更新 Node.js…」；**跨档** → 「换成稳定版」/「换成当前版」（**不叫"更新"**，见 §8.5 第 3 条）；
   **目标 == 当前** → 读数态「已经是最新版（vX）」（冻结 §1.2 R-17 的读数态，不是禁用按钮）。
3. 归属 = 版本管理器时，更新走的是**它自己的** `nvm install <目标版本>` → 切换 → 复检（§7.8），
   **不是**先重装一遍版本管理器。

### 8.2 更新前后的状态

- **更新前**：把当前版本与目标版本并排显示（当前版本来自报告里的 `node` 那一行；目标版本来自 7.2 的解析）。**目标 == 当前时按钮变成「已经是最新版（v<版本>）」**，不给一个点了什么都不会发生的按钮（也不给「检查更新」这种空动作）。**t29 补充**：并排显示的是**「当前版本（档位）→ 目标版本（档位）」**，档位判不出来时那一半写 **档位未知**（不许省略、不许猜）；**目标档位与当前档位不同时，这个动作的名字是「换档」而不是「更新」**（§8.5）。
- **更新中**：与安装共用同一套状态（下载进度 / 校验 / 安装 / 等提权 / 复检），界面上另有「正在更新」的话术。
- **更新后**：收尾**必须同时给出三个事实** —— 更新前版本、更新后版本、结论（已更新 / 没变化 / 失败）。结论由复检报告算出来，不由安装器退出码单独断言（退出码 0 也可能因为「装到了别处」而没真正生效）。

**t29 补齐（VM-15）：这三个事实都要带上"档位"，而且"更新后版本"必须是实测到的那个**：

| 事实               | 从哪来                                                                                          | 界面必须怎么写                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **更新前**版本档位 | `EnvNodePlan.currentVersion` / `currentChannel`（计划里的，动作开始前就定下）                   | `v26.9.0（当前版）` —— 档位判不出来时写 **档位未知**，不许省略、不许猜                                                                                   |
| **更新后**版本     | `EnvInstallState.observedVersion`（复检那一刻实测的 `node --version`），**不是** `plan.version` | 实测到一个与目标不同的版本时照实说（例："现在这台电脑上找到的是 v24.21.0（这次装的是 v26.10.1）"）；没测到就说没测到                                     |
| **结论**           | 复检报告 + 这次动作的档位事实（`switchesChannel`）                                              | 同档 → 「已更新」；**跨档 → 结论里必须出现「换档」这个词**（原样文案见交互规格 §10.5）；目标 == 当前 → 「版本没有变化（还是 vX）」并把「重新检测」摆旁边 |

### 8.3 风险：正在跑的 dsh 会被牵连

| 情形                                                        | 会发生什么                                                                                                      | 我们怎么做                                                                                                                                           |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| dsh 是本应用启动的，正在跑                                  | 换掉它脚下的 Node（MSI 覆盖安装时 node.exe 正在被使用，安装器可能要求先关闭；nvm `use` 会换掉全局的 node 指向） | 确认区必须写明「更新会先停掉正在运行的 dsh」，用户确认后才动手；**先停、再更新、更新完自动复检**；收尾告诉用户「dsh 已经停掉了，要不要现在重新启动」 |
| 机器上还有别的 dsh / 终端在用这个 Node                      | 那是别人的进程，我们不知道它们是否受影响                                                                        | 确认区写明「这台电脑上可能还有别的程序在用这个 Node」；**不替用户去停不认识的进程**                                                                  |
| 当前的 Node 来源无法判断（不是官方默认位置、也不在 nvm 下） | 我们不知道该用哪种方式更新它                                                                                    | **不做自动更新**：只给「打开官方下载页」+「重新检测」。这条是诚实边界，不许猜                                                                        |

**t29 落地**：上表第 3 行的"来源无法判断"现在是一个**契约事实**（`EnvDoctorReport.nodeOwner === 'unknown'`，判据与证据见 §7.7），
所以它从"诚实边界"变成了**可实施的行为**：那一行不出现「更新」按钮、给两条出路、并写明那句话。
**不许**在界面里用"路径里像不像 `nodejs`"之类的方式自己猜 —— 报告里没有这个事实时，界面的行为就是"认不出来"。

**t7 补记 ——「先停 dsh」的落点与时序（船长裁定）**：上表第 1 行那句"**先停、再更新**"必须与引擎的**实际动作同位**，
否则界面上的承诺会变成假话（历史现场：停 dsh 原先挂在安装阶段里，而"机器上已经有版本管理器"那条路**整个跳过**安装阶段，
于是"会先停掉 dsh"这句话 quietly 落空）。现在它是 `execute()` 里 `mode === 'update'` 的**唯一一处**调用
（`stopDshForUpdate()`，排在"要不要下载"的分支**之前**）：不管走哪条路、要不要下载，先停一次、也只停一次。三条要记下来的：
① **时序是「停 → 下载 → 校验 → 安装 → 复检」**，对两条路都一样 —— 这与本节"先停、再更新"逐字一致；
② **代价**：下载失败 / 用户取消下载时，**dsh 已经被停了**（旧时序是先下载、失败了不停 dsh）；
③ **这条代价被裁为可接受**：终态仍是失败（界面照旧给「重新启动 dsh」这个一键恢复的出口），
**不为它新增"dsh 已经停掉了"的额外文案** —— 重启出口已经表达了那个事实。

**pnpm 的更新没有这层风险**（改的是全局 npm 包，不影响正在跑的 dsh 进程），但**仍然要与其它动作互斥**（第 11.4 节）。

### 8.4 失败后的出路

1. 归纳过的一句话（沿用阶段一 3.4 的三类：权限 / 网络 / 包或版本不存在），认不出来就给原文尾部；
2. **安装器类失败**按第 9.2 节的三种结果分别说话（用户拒绝提权 / 用户取消 / 等太久），其中「拒绝提权」与「等太久」都要明说「系统上可能什么都没改 / 可能已经改了一部分」，并要求用户点一次「重新检测」用**事实**确认，而不是我们替他断言；
3. 永远保留「打开官方下载页自己装」这条不用代理、不用我们的网络栈的出路；
4. 更新失败**不改动**任何既有状态（不卸载旧的、不回滚）—— 我们不做半自动的版本回退，这也决定了下面这条硬要求：

> **Node 安装/更新一旦开始，我们不再杀它。** 阶段一的一键修复有「超时自动中断」（`FIX_TIMEOUT_MS` 到点 kill），因为 `npm i -g` 是可重入的、中断最坏也只是留下一个半装好的全局包。**Node 安装器不一样**：在安装进行到一半时杀掉它，会在这台机器上留下一个半装的 Node（注册表里登记了、文件不全），比不装更糟。所以安装通道的超时语义是：**停止等待，不停止安装**；按钮在那一刻从「中断」变成「不再等待（安装在后台继续）」，文案说清后果，并引导用户点「重新检测」看结果。

### 8.5 档位：目标档位跟随当前档位，「换档」是显式动作（VM-15）

**事实（VM-15 的现场）**：门禁里的默认档位是 `'lts'`，切换入口是确认区里**一行小字按钮**
（**版本档位：当前版　换成稳定版**）。用户没意识到自己选了「当前版」，于是第一步装到了 **v26.9.0（当前版）**；
而自检页的「更新」**不带档位**，主进程用默认的 `'lts'` 去解析版本清单，目标是 **v24.21.0** —— **比已经装的那个小**。
于是「更新」看起来像降级，而界面上没有一句话说这是**换档**。

**三条判据**：

1. **当前档位怎么看**：拿自检报告里 `node-version` 那一行的**具体版本号**去官方版本清单（`index.json`）里查它那一条，
   **`lts === false` → `'current'`，否则 → `'lts'`**。这与选档用的是**同一个字段**（`pickNodeRelease` 的判据），
   所以"哪一档"全仓库只有一个定义。清单里没有这个版本、或清单取不到 → **`null`（判不出来）**，
   **不许**用"主版本号是奇数 / 偶数""版本号大小"之类的猜法。
   > 为什么不能靠版本号数值猜：`v26.9.0` 是**当前版**（清单里它那一条 `lts: false`），`v24.21.0` 是**稳定版** ——
   > 档位与数值大小无关，只与官方清单里那一条的 `lts` 字段有关。
2. **目标档位跟随当前档位**（`mode === 'update'`）：不带档位意图时，**目标档位 = 当前档位**
   （当前是 current 就更新到更新的 current，是 lts 就更新到更新的 lts）。**默认值不许再是 `'lts'`** —— 那是 VM-15 的直接成因。
   `mode === 'install'`（第一次装 / 给这台机器装一个能用的）时才是设计规定的默认：**最新稳定版**（§7.2）。
3. **「换档」是显式动作，不是「更新」的副作用**（**t7 就地修正：下面两条带 ⚠️ 的原文不成立，原文保留**）：
   - ~~只有**用户显式选到另一档**（界面上的换档控件，交互规格 §4.1 第 4 条）才可能出现跨档；~~
     请求里"档位字段缺席"**永远**表示**跟随**（契约见 §11.2.1）；
   - 计划里用 `switchesChannel`（档位变了没有）与 `direction`（目标比当前新 / 一样 / **旧**）把这件事说给界面；
   - ~~**`direction === 'older'` 只可能来自显式换档**（跟随档位时，目标一定是那一档里最新的那一个，不可能更低）—— 这条要写成断言；~~
     **⚠️ t7 更正（照实现与 t12 的穷举）**：跨档有**两个**来源 —— ① 用户显式选档；② **`install` 的设计默认正好跨档**
     （机器上装着当前版、用户在向导里点「安装」→ 目标是最新稳定版 → 一次跨档，而且 `direction === 'older'`）。
     旧那句"只可能来自显式换档"**不成立**（那是这份文档写宽了，不是实现的错：t12 用 648 组合穷举过，
     `direction === 'older'` 的 108 条**全部**伴随 `switchesChannel === true`，反例 0 条）。
     **要写成断言的是另一条**：`direction === 'older'` ⟹ `switchesChannel === true`（"更新"永不降级，**按构造保证**）。
   - **⚠️ t7 补充（`switchesChannel` 的语义是超集）**：它是「**档位变了 或 目标更低**」，在 `decideNodePlan` 里一句话按构造算出来
     （冻结 §3.2.1 / §11.2.1 的 t7 标注）。`src/shared/ipc.ts` 里那句注释只写了**充分条件**（"目标档位与当前档位不同 = 这是换档"）——
     **照注释把它改回"只比档位"，就会让 `older` 重新变成一次没有解释的静默降级**（t9 的变异实验正是这么把它还原红的）。
   - **当前档位判不出来时不替用户选**：计划带 `needChoice: 'choose-channel'`，界面让用户**显式选一档**
     （选完本身就是一次显式的换档动作），并说明「我们判不出这份 Node 属于哪一档」。
4. **目标版本低于当前版本时必须明说**（这条是硬要求，原样文案见交互规格 §10.5）：
   动作名从「更新」换成「**换成稳定版**」/「**换成当前版**」，并写出「这会把现在这份 Node 换成 <档>，版本从 vX 降到 vY。」——
   两个版本号都是计划里的真值。**不许**在这种情形里出现「更新」这个词（它会让用户以为版本会变高）。

**为什么这条要与"方法"分开写**：方法是"动哪一份 Node"（§7.8），档位是"装这一份的哪个版本"。
VM-14 与 VM-15 是同一类缺陷的两个实例：**默认值代替用户做了一个只有用户能做的决定**。

## 9. 权限（提权）与网络

### 9.1 什么时候弹提权

| 问题         | 答案                                                                                                                                                        |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 什么时候弹   | **只在用户点了确认区的「开始」、安装器真的开始跑之后**。应用启动不弹、探测不弹、打开向导不弹、点开确认区也不弹                                              |
| 谁来弹       | **安装器自己**（系统级安装需要管理员权限，Windows 会在起它的时候问）。我们不重启自己为管理员、不主动请求提权、不把 `runas` 一类的东西拼进命令               |
| nvm 那条路呢 | **我们不请求提权**（v2 起安装与运行都不需要特殊权限）。安装器可能为注册事件源弹一次，**拒绝也不影响功能**，所以拒绝之后要**继续往下走**并复检，而不是报失败 |
| 界面上的说法 | 「接下来 Windows 会问你一次是否允许安装（管理员权限）」+ 在确认区里先说过                                                                                   |

### 9.2 用户的三种回应，各自的结果与话术

| 回应                                | 我们观察到什么                                           | 结论（必须由复检事实支撑）                                                   | 界面文案                                                                           |
| ----------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 拒绝提权                            | 安装器退出（非零 / 带「被用户取消」性质的编号）          | 复检后 Node 仍然是缺的 → **「你拒绝了管理员权限，这台电脑上什么都没改。」**  | 留在本步，并把「改用 nvm」放在按钮旁边                                             |
| 取消（自己点取消 / 关掉安装器窗口） | 同上（对安装器来说，用户取消与拒绝提权可能给同一个结果） | 复检后确认「什么都没改」，不编「被拒绝」的因果（分不清就说「安装没有完成」） | 「安装没有完成，这台电脑上什么都没改」                                             |
| 等太久（我们停止等待）              | 我们主动放弃等待，**不杀安装器**                         | 不给出结论；由用户点「重新检测」后由事实说话                                 | 「我们不等了：安装可能还在后台进行，请按它自己的提示把它做完，做完点『重新检测』」 |

三种结果都**不许**在没有复检的情况下断言「系统上什么都没改」——「什么都没改」这个结论本身就是一次探测的产物（这也是唯一能让用户安心的说法）。

### 9.3 网络：不许假定用户有代理，也不许忽略用户已经有的代理

| 场景                          | 要求                                                                                                                                                              |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Node / nvm 安装包下载         | 默认走官方直连；**必须遵循系统代理设置**（Windows「设置 → 网络和 Internet → 代理」里配的那种）—— 不要让用户为了我们的下载去填一次代理，也不要无视他已经配好的代理 |
| 下载不通                      | 三类归纳（超时 / DNS / 连接被重置）+ 三条出路：官方下载页（用浏览器，浏览器有自己的代理）、换一个下载源、装好后「重新检测」                                       |
| npm registry（装 pnpm / dsh） | **复用阶段一已有的「插件安装源」设置**（阶段一已把它注入一键修复的子进程环境，且**不写用户的 `.npmrc`**）：用户填过就用他的，界面上写明「本次使用你设置的安装源」 |
| 企业内网 / 完全不能出网       | 不假设有代理，也不假设有外网：给「填一个内部源」与「自己装好再重新检测」两条路；一键装不了不许说成「失败」，要说清「这台机器连不上外网，可以这样绕过去」          |
| nvm 自己去哪儿下 Node         | nvm 有自己的镜像设置（它的配置文件），**我们不替用户改那个文件**：界面上显示它当前的值与「怎么改」的命令，让用户决定                                              |
| 一个坑要写进文案              | 国内常被推荐的那个「淘宝旧镜像」域名早已停服；若用户的安装源指向它，要单独点出来（阶段一的失败归纳里已有这条判断）                                                |

## 10. 在一台没有 Node 的纯净 Windows 11 上第一次跑，会发生什么

逐条回答（每一步都是可实现的、可验收的；失败分支见括号）：

1. 用户装好 DSH Console 并启动。应用自己的界面能起来 —— **它自带 Electron 与 Node 运行时**，不依赖机器上的 Node。既有的启动锁不会立刻扣上来，因为启动流程要先等探测结果（5.2 的顺序要求）。
2. 主进程做**只读**探测（不写盘、不放行任何动作）。这台机器上的结果是：外部 Node 找不到（版本项因此也没有判据）、npm 找不到、pnpm 找不到、dsh 本体找不到、**「dsh 能不能跑」测不了**。注意：在这种情况下 **`npx` 兜底也不存在**（npx 自己也要 Node），所以「dsh 那一行」的出路实际上只有一个 —— 先把 Node 装上。
3. 判定：Node 步骤是 `todo`（有证据的缺失）→ 门禁 `blocked` → **显示门禁层**；**不自动拉起 dsh、不自动打开 Harness、不进全屏**（避免先失败一次再解释）。
4. 门禁层显示「第一步：安装 Node.js」+ 一句为什么 + 两个选项（直接安装官方稳定版 / 用版本管理器装）+ 「打开官方下载页自己装」+ 底部常驻的逃生口。
5. 用户点「直接安装」：确认区显示**具体版本号**、安装包名、下载来源主机名、「需要管理员权限，Windows 会问你一次」、会装到哪里、会改什么；用户点「开始」。
6. 下载：显示百分比，可取消（取消后系统没有任何改动）。
7. 下载完成 → 先比哈希（与官方校验清单不一致 → 删掉临时文件、**不安装**、给「打开下载页自己装」的出路）；再读安装包的数字签名 → 读到有效签名就记录签名者，读到**明确未签名 / 无效**就不安装，读不到就继续装并在结果里如实写「这次没能读到安装包签名」（见 7.3 第 2 条）。
8. 安装：Windows 弹出提权询问（用户拒绝 → 见第 9.2 节，留在本步，旁边给出「改用 nvm（不需要管理员权限）」）。
9. 安装成功 → 重读系统里的环境（7.4）→ 自动复检 → Node 步骤变绿（此时 npm 也随 Node 一起装好了，它显示在这一步的展开详情里）。
10. 门禁层前进到「第二步：安装 pnpm」→ 一键安装（阶段一已实现的动作）→ 复检变绿，或者用户点「跳过」（跳过是知情的，会持久化并在界面留标记）。
11. 「第三步：安装 dsh」→ 一键安装（阶段一已实现的动作）→ 复检 → **「dsh 能不能跑」那一项实测有输出**才算这一步完成（退出码 0 但零输出＝静默退出，仍然待办，出路是「换一个 Node」）。
12. 三步都完成（或可跳过的已跳过）→ 门禁 `open` → 出现「进入 DSH Console」按钮（**不自动跳走**）。
13. 用户点进入 → 走阶段一的正常流程：自动拉起 dsh（`autoStart` 为真时）→ 就绪后按既有设置自动打开 Harness、按既有设置进全屏。
14. 之后想换版本：环境自检页的「更新 Node.js」/「更新 pnpm」（第 8 节）。
15. **任何一步的任何一个时刻**，用户都可以点逃生口进入主界面（5.4）；主界面会常驻一条横幅，点它就能回到向导。

**如果中途关了应用**：下次启动重新探测、重新判定，因为「跳过」是持久化的、而「逃生」不是 —— 逃走过一次不等于以后都不挡（这是硬门禁的本意）。

**三条不可动摇的约定**（与阶段一 3.2 同款）：

1. **渲染层只递选择，不递命令、不递 URL、不递哈希**：`envNodePlan` 是给用户看的，安装时主进程**现场重算**（照抄阶段一 `envFix` 只接受 `action` 的做法）。否则渲染层递来的 URL 就是一个可被替换的下载源、递来的哈希就是一个可被替换的校验依据。
2. **spec 是一个 argv，不拼 shell**：安装器与 nvm 的调用都经 `process-utils.ts` 的 `launchSpec()`（`.cmd` / 批处理在 Windows 上要经 `cmd.exe` 并带 verbatim）；新代码**不许**出现 `shell: true`。
3. **环境按既有规矩补**：`envWithKnownBins(process.env)`（保留系统原有的 `Path` 键名）+ 安装源设置；不改用户的 `.npmrc`、不写系统 PATH。

**为什么不扩 `EnvFixAction`**：阶段一的 `EnvFixAction` 是「只改全局 npm 包」的两个动作（阶段一 3.1），它有可中断、超时自动 kill 的语义；Node 安装既不是 npm 包，中断语义也相反（第 8.4 节）。把它塞进同一个联合，就会让「超时 kill」这条既有规则在一条不该 kill 的路径上生效。所以**一个通道一个类型**，`EnvFixAction` 保持两个成员不变 —— 既有断言「契约里有 8 个 id、2 个动作、5 个 API」因此**不需要改**（它检查的是这几个成员在不在，不是排他）。

### 11.4 互斥：一把全局锁

阶段一的互斥位只覆盖两个 npm 修复动作。这一轮引入 Node 安装之后，**同时只能有一个会动系统的动作在跑**（装 pnpm / 装 dsh / 装或更新 Node）。理由是一样的（两个动作同时改一台机器，结果不可预期），只是范围变大：安装通道与修复通道共用同一个「忙」位（同步置位、终态释放，照抄阶段一 3.2 第 6 条与既有断言「环境自检：单动作互斥是同步置位」）。界面上「正在装 Node」时，其它动作的按钮必须是禁用态，而不是点了之后回一句「已经有一个动作在进行中」才算数（后者也可以，但按钮态更清楚）。

### 11.5 不进契约的东西

- 下载 / 校验 / 安装 / 重读系统环境的实现（留在主进程的安装引擎模块里）；
- `judgeWizard` 的实现（放主进程，纯函数，导出给自检；**不进契约** —— 契约管的是跨进程线缆上的形状）；
- 逃生口的「本轮已逃生」标记（渲染层内存状态，不写盘、不过线缆）。

## 14. 明确不做的事

- **不做便携 ZIP 的 Node 安装**（第 7.1 节的理由：不写系统 PATH 就会造出第二个事实来源）；
- **不在归属已知时提供"再装一份"的入口**（§7.8）：归属 = 版本管理器时**不出现**「直接安装官方版本」、归属 = 官方安装包时**不出现**「用版本管理器安装」。只有 §7.8 那三个例外（每一个都由用户**显式**点名 + 确认区先说清两份并存的后果）才出现第二条路；
- **不做「跳过门禁」的开关**（逃生口已经覆盖了真实需求，见 11.3）；
- **不主动提权**：不重启自己为管理员、不拼 `runas`；提权只由安装器自己触发；
- **不改系统 PATH、不写用户的 `.npmrc` / `nvm` 配置文件**：只**重读**系统里已有的环境（7.4）与**注入这一次子进程**（安装源）；
- **不做静默安装**：任何改动前都要有确认区（与阶段一 3.1 的第 5 条同款）；
- **不做自动回滚 / 自动卸载**：更新失败就停在原地并说清事实（第 8.4 节），不替用户做回退；
- **不做定时轮询的环境监控**：环境不会自己变（阶段一 9 的同一条理由），只有启动一次 + 用户点一次 + 动作跑完自动复检一次；
- **不做 macOS / Linux 的自动安装**：这一版的门禁与 Node 自动安装**只在 Windows 上生效**；其它平台保留阶段一的只读探测与既有两个一键动作（外加「打开官方下载页」），门禁不拦（不提供一个点了必然失败的门）；
- **不把「正在跑的 dsh」之外的进程停下来**（8.3）；
- **不在诊断与文案里输出任何凭据或环境变量的值**（阶段一 9 的同一条理由：路径可以打，值不行）。
