向导结束后的自动启动，要不要上启动锁

你要的这条我读代码确认了现状：放行页点「进入 DSH Console」（或点逃生口）之后， app.ts 的 wireGateAutoStart() 会自己 api.start() 拉起 dsh， 但**故意不上锁** —— 这是冻结表 R-07 当初的裁定（「逃生 / 放行之后的自动启动不出现启动锁」）， 理由是启动锁当时只能**单向推进**，要重新上锁就得改成"每次状态变化重新判定"，而那正是 AGENTS §7.9 修掉的那个 bug（解锁之后条件又变回不满足，锁又扣上来）。

所以这次不是把 R-07 删掉，而是给启动锁加一个**显式的第二回合**：只有「向导结束 → 自动启动」 这一件事能请求上锁，其它任何状态变化都不会让锁回来（下面 §3 第 ③ 条）。要请你定的是两件事： 哪些离开方式上锁、锁上写什么。

1. 哪些离开门禁层的方式要上锁选一个

两种离开方式都会触发自动启动（今天就是这样）；差别只在"要不要把用户按住等"。逃生口那条路上环境 本来就没配好，dsh 很可能起不来（锁会立刻因为"异常相位"解锁 —— 也就是闪一下）。

A. 只有放行页点「进入 DSH Console」（我建议这个） 语义最顺：放行页的意思是「环境好了，进去吧」，进去时锁一下等 dsh 是合理的；而逃生口写的是 「环境还没准备好，我稍后自己处理」—— 用户已经明确说"不等了"，再按他一下与他刚说的话相反。

逃生口那条路：**不上锁**（照现在的样子：主界面 + 状态栏「启动中」）。

2. 锁上写什么选一个

A. 与启动时完全一样（我建议这个） 两处走的是同一个状态机、同一张卡：标题「正在启动 dsh 服务」+「正在拉起进程并等待健康检查」+ 「已等待 N 秒 · 就绪后自动打开 DeepSeek Harness 并进入全屏」+「不等了，先进入界面」。 用户不需要知道"这次启动是向导之后触发的" —— 他知道的是"dsh 正在起"。

3. 三条固定规则不是选择，是这条改动的边界

  1. 没有等待就不上锁：dsh 已经在跑、或这一轮只是接管了外部实例时，自动启动是空操作 —— 这时**不显示锁**（否则只是闪一下）。判据是主进程回报的相位，界面不自己猜。
  2. 解锁条件与启动锁完全一样：dsh 就绪（该开的页面也开了）/ 异常相位 / 超过 90 秒 / 点「不等了，先进入界面」/ 按 Esc。锁永远只是免打扰，不是把人关在外面。
  3. 不改成可重入，只加一个"显式的第二回合"：状态机仍然是单向的，只是允许 armAfterGate() 在"向导结束 → 自动启动"这一刻开一个新回合（一次运行里每个回合 最多锁一次）。这样既拿到你要的效果，又不会回到"某次无关的状态变化又把锁扣上来"那个 bug。 与门禁层的互斥照旧：--z-gate（58）低于锁（60），交接的那一帧永远是锁盖住门禁。
